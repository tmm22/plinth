# Slant 3D V2 API integration reference

Verified 18 October 2026 from [official documentation](https://slant3dapi.com/documentation/introduction) (docs SPA bundle `assets/index-DSzyXtco.js`; `assets/index-BcaZVnjh.js` on 29 Oct 2026; `assets/index-C5Wnw4hq.js` since 9 Nov 2026 (HTML `Last-Modified: Mon, 09 Nov 2026 19:42:53 GMT`, deployed with the spec revision of 19:42:24 GMT; read 12 Nov 2026, when the earlier bundle was no longer served)), and [official OpenAPI](https://slant3dapi.com/v2/api/openapi.json). The bundled `Sources/Plinth/Resources/openapi.json` is the official spec plus supplements marked with `x-plinth-source: docs` (from Slant's docs) or `live` (seen in Slant's replies, nearly always to read-only requests); `slant-openapi-upstream.json` beside it is Slant's spec as last reviewed (see [Keeping up with Slant's API](#keeping-up-with-slants-api)).

## Connection and prerequisites

- Production base: `https://slant3dapi.com/v2/api`. Bearer API key in `Authorization`, JSON bodies with `Content-Type: application/json`. Do not send bearer credentials to presigned storage URLs.
- Exception: `POST /slant/webhook` uses `https://slant3dapi.com/v2/slant/webhook`, outside the `/api` prefix (operation-specific server in OpenAPI).
- Rate limit: **100 requests/minute** per API key. Response headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (epoch **milliseconds**, live 23 and 29 Oct 2026; Slant's docs say "Unix timestamp" and their sample multiplies it by 1000; `rateLimitResetDate` also accepts epoch seconds, reads a small number as seconds from now, and ignores negative, unparseable or more-than-a-day-away values), `X-RateLimit-Role`. The public `/health/status`, `GET /apiKey` and the authentication layer's 401s send none of these, so Plinth keeps the last known values whenever a response carries no rate-limit headers. OpenSCAD: **100 generations/hour** by Slant's spec and docs since 9 Nov 2026 (it said 5 before; not verified live: Plinth sends at most 5 an hour until a generation reply's own `X-RateLimit-Limit` states the limit, and raises its cap only when that reply's reset is more than two minutes ahead, never above 100), one in flight. Up to three API keys and five enabled platforms. No public sandbox.
  - What `X-RateLimit-Reset` marks is unresolved (read-only GETs). Some replies give a fixed time up to about 60 s ahead that stays put while `X-RateLimit-Remaining` falls (a 13-digit epoch-ms value 60 s after the request on 23 Oct 2026; on 29 Oct 2026 one value held for 14 s while Remaining fell by ten). Others give a time only a few seconds ahead that moves later with each request while `X-RateLimit-Remaining` stays level or goes back up by one (29 Oct 2026), as a sliding 60 s window would. Either way, waiting until Reset may free only one request, so every paced batch checks the figures again before its next call.
  - `GET /usage` reports `rateLimitConfig.blockDurationMs: 60000`; whether a 429 blocks the key for that long, and which headers a 429 carries, are unverified. So after a 429 it receives, each of Compare estimates, Check Cost, Import Orders, Pay Several Drafts and Load the Whole Period sends nothing more for at least 60 s (`comparisonRateLimitedUntil`), whatever Reset says; a 429 one of them receives doesn't hold the others (Import Orders also waits out the recent-orders read's). A single request's 429 message names the same wait (at least 60 s, or Slant's longer `Retry-After` or reset); it is advice only, and Try Again resends only reads and the estimate. The order watch has its own backoff, and Personalise from Template's hourly OpenSCAD limit is separate (below).
- Most workflows require an owned platform. Drafting does not charge; processing charges and starts production. Key creation/listing (`/apiKey`) is session-only (dashboard): with an API key, `GET /apiKey` is 401 `{"error":"Unauthorized","message":"Please log in to access this resource"}` (29 Oct 2026).
- Requests to the Slant API carry `User-Agent: Plinth/<CFBundleShortVersionString, else "dev"> (macOS <version>)` and `Accept: application/json` (OpenSCAD: `Accept: application/sla, application/json`); presigned storage PUTs and file downloads don't carry Plinth's User-Agent (only URLSession's default one). The key goes with every request to Slant's API host, the public `/health/status` included. Query values are percent-encoded including `+` (`%2B`), because Slant's server reads a bare `+` as a space (`slantAPIURL`).
- Errors (read-only GETs, 28–29 Oct 2026): `{"success":false,"error":{"message":"…","statusCode":400}}` (not the spec's `ErrorResponse`, whose `error` is a string), and no request-ID header is sent. The authentication layer answers differently: an unauthenticated 401 is `{"error":"Unauthorized","message":"Bearer token required in Authorization header","format":…}`, an invalid key gets the same shape with "Invalid API key", and an endpoint above the key's role is 403 `{"error":"Forbidden","message":"Minimum role required: admin","requiredRole":…,"currentRole":…}`. `GET /orders` 400s name the parameter, such as "Invalid limit passed on query: 201. Limit maximum is 200". `shortAPIMessage` reads `message`, then `error.message`, then `error`. Quoted messages pass `apiMessageRedactingCredentials`, which masks bearer values and Slant keys in either form, `sl-…` (the docs, the `/usage` key prefix and live keys) or `sl_…` (the spec's `ApiKeyAuth`). The spec also documents 401 for "Order belongs to another creator" / "File belongs to another creator", so Plinth says to reconnect only when a 401 has no message or one about the token, key or authorisation, and otherwise quotes Slant ("Slant refused this request. …"). A 409 is worded as a conflict (refresh before trying again), since Plinth treats it as an unknown outcome for writes. A 2xx whose envelope says `success: false` stays an unknown outcome; its message is quoted. A numeric `Retry-After` (not documented by Slant) gives the wait in the 429 copy; otherwise `X-RateLimit-Reset`.

## Upload and manufacture

1. `POST /files/direct-upload` with `name`, `platformId` required; `ownerId` optional; `type` optional `stl` | `3mf` | `obj` (default `stl`); `POST /files` takes the same values, but its docs mark `type` required ("Defaults to stl. Required if uploading a different type"), so Plinth always sends it there. The guided Models upload sends the library file unchanged in its original format, omitting `type` for STL and sending `obj` or `3mf` otherwise. OBJ/3MF preview, unit conversion and **Save STL copy** are local only; Plinth never sends its converted copy unless you upload it as its own model.
   - **Slant converts 3MF uploads to STL** (live, 29 Oct 2026): every file record reads `type: "stl"` with a `.stl` storage key, including two 3MF uploads (21 and 23 Oct 2026), whose stored bytes (a ranged GET of `fileURL`) begin `Binary STL converted from 3MF by file-service`. Slant's docs list obj, 3mf and stl in their File Structure and say of `fileURL` "Only the STL file can be downloaded", which fits; the spec's own `File.type` (`["stl"]`, "currently only STL supported") is right for records. The bundled `File.type` keeps `stl`, `obj` and `3mf` (now tagged `live` with this note) because `confirm-upload` sends that schema back as `filePlaceholder`, and the Workbench validates it. So **Download into Library** of a 3MF upload gets Slant's STL conversion (`cloudDownloadExtension` reads `stl`), without the 3MF's units or Source and licence details. Unverified: whether OBJ uploads are converted the same way and what an OBJ record's `fileURL` serves, and how the conversion treats 3MF units other than millimetres or files that place several objects (that decides what Slant prints).
   - **Slant files an upload under its name** (live, 30 Oct 2026). Slant's docs say a file's `name` is "Sanitized before storing. Unique to ownerId" (the spec doesn't); with no `ownerId` sent, every file's `ownerId` equals its `creatorId`, which Plinth reads as unique across the account (an inference: whether `creatorId` names the account or the API key is unverified; the docs' Update File Owner ID note says a file uploaded under another API key gets a 403). Two uploads named “Studio name test” (the same small STL) showed what it does: the second `POST /files/direct-upload` returned the same `filePlaceholder` as the first (the same internal `id` and `publicFileServiceId`) and the same storage key (`…/<id>/Studio name test.stl`), before any bytes were sent; both confirms returned the same `publicFileServiceId`, and `GET /files` lists one record. So an upload whose name matches one of the owner's files reuses that file's record, and its PUT writes over the same storage object: every draft, and possibly every order, that uses that `publicFileServiceId` then prints the new contents. The two test files were identical, so the replacement is inferred from the shared key, not observed. Unverified: whether the match ignores case or the extension, whether a paid order's print is affected, and whether `POST /files` (Upload from URL) does the same, which is likely.
   - What Plinth does about it. **Upload Model**, **Upload Again…** and **Upload from URL…** first compare the name with your whole Slant file list (`checkUploadName`, `slantUploadNameConflict`). Slant's rule is unknown, so the comparison errs towards a match (`slantUploadNameKey`): trimmed, runs of spacing collapsed, any case, and trailing `.stl`, `.obj` and `.3mf` endings ignored (never down to an empty name). A model linked to a listed cloud file is checked under that file's name, so its own earlier upload is the one offered (`slantUploadNameCheckResult`). Before every such upload Plinth reads every page of `GET /files` afresh: read-only, no `platformId` (names are unique per owner), pages of 100 (Slant's docs allow `limit` 1–200, default 50, and `sortBy` createdAt|updatedAt|name|type with `sortOrder`; unverified live for files), 0.6 s apart, at most 50 pages. That read only feeds the check and the guard below; it doesn't change the Models file list. It stops before each page while `X-RateLimit-Remaining` is at or below the order watch's reserve of 20 (until `X-RateLimit-Reset`, or for a minute when no reset time came back), and after a 429 no check reads again until the latest of `X-RateLimit-Reset`, a numeric `Retry-After` and 60 s from now (`slantUploadNameCheckRateLimitStop`, `comparisonRateLimitedUntil`). If the read fails, stops for the rate limit or returns a page without file names, nothing is uploaded and the message says to upload again (Upload from URL shows it in its sheet); the alert offers no **Try Again**, and the check is never retried. More than 5,000 files is a final refusal, with its own message. When a file has the name, a confirmation titled “This name is already in your Slant files” says “A file named “X” is already in your Slant files. Uploading with this name replaces that file for every draft that uses it, and possibly for orders not yet printed.”, adding when the match is this model's own earlier upload (or may be an upload Slant didn't confirm), and offers **Upload as “X 2”** (the first “X N” that no file just read, or already loaded, has, with a `.stl`/`.obj`/`.3mf` ending kept last, `slantUploadUniqueName`), **Replace File** and **Cancel**, the default (Escape); no keyboard shortcut sends. **Upload Again…** shows one dialog: that one, or, when the name is free, a single confirmation that it uploads as a new file. Import Orders' personalised uploads end in a short random token instead (eight hex characters from a fresh UUID, such as “Etsy order 123 personalised 1 of 2 · 7f3a9c21”), so no two of them share a name in a batch or a session, and they need no check. When a confirmed upload returns a `publicFileServiceId` that another library model is already linked to, the link stays only on the model just uploaded, because that cloud file now holds its contents (`modelsLosingLinkAfterUpload`; after Upload from URL, which links no model, no library model keeps it).
   - **The pre-PUT guard** (`APIClient.upload`'s `checkPlaceholder`). Slant returned the existing file's `filePlaceholder`, with its `publicFileServiceId`, from step 1, before any bytes were sent (above), so Plinth checks that `publicFileServiceId` before the PUT and stops with nothing sent when it names a file that must be kept (`uploadPlaceholderProtectedFile`, `UploadWouldOverwriteExistingFile`): for Models, every file the name check just read or had loaded and every library model's link, less the one the seller chose to replace (`uploadProtectedFiles`, `uploadProtectedFilesAddingLibraryLinks`); for personalised uploads, the loaded files, every library model's link and the files this batch already uploaded (`batchPersonaliseProtectedFiles`), and such a stop skips only that order, as a refusal. A placeholder without a string `publicFileServiceId` can't be checked and passes. A Replace File also stops there when the placeholder names any file other than the one chosen (`uploadReplacePlaceholderMismatch`), and is sent under the listed file's own name, the one form Slant is known to match. `presignedUrl` and `fileURL` must pass `storageLinkProblem` (https, a named host that isn't local or an IP literal, port 443, no user info or fragment), checked before any bytes or request; there is no host allowlist. Upload from URL is one `POST /files`, with no placeholder before Slant stores the file, so the guard can't run there.
   - **Replace File unlinks first.** Before anything is sent, a Replace File clears every library model's link to the replaced file and saves the library (if that save fails, the links are put back and nothing is sent), so a quit, a crash or a reply without a file ID can't leave a model linked to a file that may now hold other bytes; only a confirmed Models upload links the uploaded model again. If the upload then stops with nothing sent, those links stay cleared and the message names the models. Quitting asks first while a Models upload or an Upload from URL waits for Slant (`SlantWritesInFlight`).
   - Local preview limits (client-side, `ModelFormats.swift` / `ZipArchive.swift`): 128 MB file and 500,000 triangles for every format. 3MF: at most 128 MB expanded in total, 10,000 ZIP entries, 1,000 model parts, component depth 32 and 100,000 placements (applied to both the triangle-count and the placement pass); entries over 1 MB that expand more than 200:1 are refused, as is any DTD (`<!DOCTYPE`/`<!ENTITY`, checked in UTF-8 and UTF-16 and by the XML parser's declaration callbacks). OBJ: lines up to 64 KB; polygons are ear-clipped on their best-fit plane (convex faces keep the fan from corner 0) within a per-file work budget; a face that crosses itself, or one over the budget, is previewed as a fan and blocks STL and scaled copies of that file.
2. PUT raw bytes to `data.presignedUrl` without Authorization, with `Content-Type: application/octet-stream` (works live); retain `data.filePlaceholder` unchanged.
3. `POST /files/confirm-upload` with `{ "filePlaceholder": <exact object> }`. Identifier is `publicFileServiceId`. Prefer `metrics` over deprecated `STLMetrics`.
   - Docs (read 28 Oct 2026): uploads up to 250 MB and the 220 mm cube; at most 500 uploads a day per platform (upload tokens per platform reset every 24 hours); confirm every upload, and "upload and confirm files in batches of 2 to avoid issues with file analysis". Plinth uploads one file at a time. The Models upload words a failure by its step (`uploadFailureMessage`): no usable link from step 1 or a refused or expired storage link in step 2 (a storage 403 isn't about the API key) means nothing was stored, unless it was a Replace File (below); after step 3 anything but a definite refusal (timeout, transport error, 5xx, 408/409, an unreadable or `success: false` reply, or a 2xx without a file ID) leaves the file possibly on Slant, so Models suggests Refresh and asks before uploading again (a standard key can't delete files). After **Replace File**, which reuses the existing file's record and storage key, a failure once the PUT may have started (any step-2 failure, or any step-3 failure, even a definite refusal, because the bytes may already be stored) is worded as possibly having left that file holding part of the new model for every draft that uses it (`uploadReplacementMayBePartial`, `uploadReplacementPartialMessage`): every library model linked to that file, this one included, loses its link, the selected file and estimate are cleared when they point at it, and the message names the models to upload again. Upload from URL's **Replace File** does the same after an unclear reply (`uploadFromURLReplaceUnclearMessage`). This is a precaution: whether a failed storage PUT can leave a partial object is unverified. Only a real file ID links the upload, never the name: `publicFileServiceId`, else `publicId`, else `id` only when it is a non-empty string (the docs' `filePlaceholder` example has `"id": 9999`, an internal number). Nothing is retried.
   - A file Slant hasn't measured (no measured `metrics`) offers **Check Again**: one read-only `GET /files/{publicFileId}` per press, merged into that row; nothing checks by itself. Slant can leave a file unmeasured indefinitely: one 3MF upload (23 Oct 2026) still had every `metrics` and `STLMetrics` value `null` apart from `units` on 29 Oct 2026, while the other converted 3MF was measured, so the cause isn't known. Neither the docs (metrics "read null until the file has been analyzed") nor the spec describe a failed analysis. So Model analysis says Slant is analysing only a new upload; once the upload is more than about an hour old it says Slant hasn't measured the model since it was uploaded on that date and suggests uploading the model again (`metricsPendingCaption`, after `metricsPendingStaleAfter`, one hour; with no readable upload date it stays “Analysing…”); that upload goes through the same-name check, where Upload as “X N” keeps the old file and Replace File reuses it. It doesn't say why, or that estimates will fail. Download into Library first reads the file again (`GET /files/{publicFileId}`), because the docs give `fileURL` "a Lifespan of 1 hr … Refreshed on GET request for file", then reads that `fileURL` with no Authorization (the docs' examples use `slant-gatekeeper.s3.us-west-2.amazonaws.com` for `presignedUrl`, `fileURL` and preview images; unverified live), refuses redirects, writes the chunks URLSession delivers straight to a temporary file and stops above 300 MB (Content-Length or while reading).
   - `metrics.units` (live, 29 Oct 2026, every file listed) gives one unit for all three sizes under `dimensions` (`mm`), beside `weight` (`g`), `volume` (`cm3`), `surfaceArea`, `printTimeEstimate` (`min`) and the support estimates. Plinth reads `units.x`/`y`/`z` when present, else `units.dimensions` (`metricUnit`), skips a null or empty unit, and otherwise assumes mm, g, cm³ and minutes.
4. Estimate with `POST /files/{publicFileId}/estimate`. Draft with `platformId`, customer details/address, and items. **Get Estimate** applies Compare estimates' check (`comparisonPrice`): a reply without a usable `total`, or for another `quantity`, is shown as a failure, not an estimate.
   - Request: `{ "options": { "filamentId": <uuid>, "quantity": <int ≥ 1> } }`; both optional (PLA Black, quantity 1). Response `data`: `subtotal` (before surcharges), `total` (estimated print cost, USD), `pricePerUnit`, `quantity`, `totalMaterial`, `estimatedPrintTime`, `bodyChargeCost`, `oversizeSurcharge`. No delivery cost: shipping is priced only by the order draft (`totals.deliveryCost`). The OpenAPI gives no unit for `totalMaterial` or `estimatedPrintTime` and says `subtotal` and `totalMaterial` are for the quantity requested; the docs' example has `subtotal` equal to `pricePerUnit` at quantity 5 and a one-unit `totalMaterial`. Live, 23 Oct 2026, on a converted 3MF (quantity not recorded): `estimatedPrintTime` 6.66 against the file's `printTimeEstimate` of 402 minutes, which is within 1% of 402 ÷ 60, so it may be hours (one observation; undocumented); `subtotal` 7.64 against `pricePerUnit` 9.93 with both surcharges 0, which fits neither reading. So Plinth shows the total, price per unit and any non-zero surcharge, and leaves print time and weight to Model analysis (`metrics`, documented as minutes and grams).
   - Observed 25 Oct 2026 (three uploads of a 40×40×20 mm STL, PLA, quantity 1; Plinth's strength test): a plain block reported `metrics.bodyCount` 1, `bodyChargeCost` 0, `total` 1.91, `weight` 18.04 g, `printTimeEstimate` 104; the same block with nine closed internal voids (0.25 × 35 × 17 mm) reported `bodyCount` 10, `bodyChargeCost` 3.50 (about $0.39 per extra body), `total` 6.95, weight 29.62 g; the same slots open through the bottom face reported `bodyCount` 1, `bodyChargeCost` 0, `total` 2.43, weight 30.45 g, `printTimeEstimate` 134, `supportAreaEstimate` 78.75 mm² with `supportRequired: false`. So closed voids are billed as bodies, surface-open slots aren't, and the slicer prints walls round the slots. Plinth names the charge “Charge for N extra bodies” using the estimated file's own `bodyCount`.
   - Slant's published print-on-demand settings (Slant blog settings graphic, read 25 Oct 2026), not changeable per order or by API (`items[].options.slicerOptions` has no active overrides): 0.2 mm layers, 0.3 mm first layer, 1 mm walls, 25% infill, 50° overhangs, no brims, 0.4 mm nozzle, 220 mm cube, textured bed; uploaded orientation kept unless obviously wrong; supports decided at upload. Unpublished: line width, tolerances and the slicer used.
   - One material and one quantity per call; there is no batch estimate. Estimates are side-effect free and the only POST the error alert's **Try Again** may resend (`StudioStore.RetryAction`: GETs plus the estimate, pinned by `ShellUXTests.testEveryRetryActionIsReadOnlyOrEstimate`); Plinth never retries anything automatically.
   - **Compare estimates** (`EstimateComparison.swift`; offered once the model is uploaded and materials are loaded) issues up to 20 of these calls (≤ 4 materials × ≤ 5 quantities), strictly sequentially and at least 0.6 s apart (100 requests/minute). Before each call it stops, keeping completed results, when `X-RateLimit-Remaining` ≤ 10 and `X-RateLimit-Reset` is in the future (without a reset header, a low count is trusted for 60 s), after a 429 (blocked until the latest of `X-RateLimit-Reset`, a numeric `Retry-After` and 60 s from now, at most an hour), on 401/403/404/408/409/5xx or a transport error, after 3 consecutive per-cell failures (400/422 or a response without `total` or with a different `quantity`), or when the selected file, connection or global busy state changes. It does not set the app-wide busy flag. Rate-limit state is updated only from responses that carry `X-RateLimit-*` headers. Quantities are whole numbers from 1 to 10,000 (ambiguous input such as `1,500` is refused). Per unit is computed as `total ÷ quantity`; `total` is after surcharges (`subtotal` is before them), so surcharges are spread across the units. A cell applied with **Use** becomes the current estimate under the same `fileID|filamentID|quantity` context as **Get Estimate**.
   - **Check Cost** (Saved Products, `ProductCostCheck.swift`) sends the same request once per print line of a saved product, with `quantity` = the line's quantity × the units typed (once-per-order lines: the line's quantity alone) and the line's `filamentId`: at most 20 calls, with Compare estimates' spacing, rate-limit stop (≤ 10 remaining, or after a 429) and no retries, stopping after 3 prints in a row fail. It doesn't set the busy flag; it won't start while busy and stops before the next call if another task starts. Components and stationery are priced from the loaded catalog (`price` × quantity, USD only) without a request. Results are session-only; Activity records counts only.
5. Draft response `data` shape (docs): `{ order, items, totals: { printingCost, deliveryCost, totalCost }, customer }`. The docs give `totals` "as numbers" (example 35.53); the order's own `printingCost` and `deliveryCost` are strings in the docs and live. Whether the live draft reply's totals are numbers is unverified, and Plinth reads either (`orderStrictAmount`, `decimalAmount`). The docs' draft-reply items also carry `fileURL` (`"Unknown"` for a print), `componentName` and `stationeryName`, which the spec's `OrderItem` lacks.
6. Process with `POST /orders/{publicOrderId}`; cancel with `DELETE` (see refund note below). The pay reply's shape is unverified live: the docs say every order endpoint but Get Order returns the order directly on `data` (their example has `data.status: "SUBMITTED"`), while the spec says `data.order`. Plinth reads both (`orderObject`), and the pay outcome rules don't depend on which. OpenSCAD returns raw STL bytes (`application/sla`).

## Delivery address defaults and lookup

The guided order composer defaults the shipping country from the Mac’s Region setting, with delivery details reused from the current session taking priority. Region is an editable default, not physical-location detection.

**Use Current Location** is an optional client-side Apple Core Location and reverse-geocoding flow, not a Slant endpoint. It requests permission only after the button is pressed and offers a suggested street address for review. **Use This Address** replaces shipping fields, clears the old apartment/unit number, and retains name and email. Coordinates are not added to the Slant order payload or activity log. The reviewed address is sent through the normal order-draft request when the user creates the draft.

The app rejects fixes older than 60 seconds or with horizontal uncertainty over 100 metres, and stops lookup after 45 seconds. These are app heuristics, not delivery-address verification. Missing street/country information, lookup errors and denied permission leave manual entry available. See `DeliveryLocation.swift` and the permission descriptions in `scripts/build-app.sh`.

## Orders, fulfillment, cancel / refund

- **Order statuses since 26 Oct 2026** (live OpenAPI and docs, checked with read-only GETs on 28 Oct 2026): `DRAFT` ("Drafted and not yet processed. Nothing has been charged or sent to production"), `SUBMITTED` ("Processed and paid. The order is with us and waiting to print"), `PRINTING` ("In production: printing, finishing and packing"), `SHIPPED` ("Handed to the carrier. Tracking is on fulfillment.trackingNumbers") and `CANCELLED` ("Cancelled before it shipped"). `GET /orders?status=` takes exactly these five (case-insensitive) and refuses any other value with 400 “Invalid status filter”. Orders paid before the change read `PRINTING` on 28 Oct 2026. Plinth shows Submitted with the hint “Paid, waiting to print” and Printing with Slant's “In production” description.
  - The earlier 14-value set (`DRAFT`, `PAID`, `QUEUED`, `PROCESSING`, `PRINTING`, `ITEMS_ON_SHELF`, `POST_PROCESSING`, `COMPLETED`, `IN_REVIEW`, `AWAITING_SHIPMENT`, `SHIPPED`, `DELIVERED`, `CANCELED`, `PAYMENT_ERROR`) is no longer returned. Plinth keeps those values only to read saved order-watch snapshots and old replies (`orderLegacyStatuses`), never offers them as a filter, and treats Slant's re-labelling of a saved status (to `SUBMITTED` or `PRINTING`, `CANCELED` → `CANCELLED`, `DELIVERED` → `SHIPPED`) as no change.
  - Spelling: the live value is `CANCELLED`; the earlier one was `CANCELED`. Plinth accepts both (`orderStatusIsCancelled`) and shows “Cancelled”.
  - **The order status can lag the shipping record** (read-only GETs, 29 Oct 2026): two paid orders read `status: "PRINTING"` while their `fulfillment` was `{status: "SHIPPED", provider: "SHIPPO", deliveryMethod: "INTERNATIONAL", trackingNumbers: [one number], labelPrinted: true, providerStatus: null}`, with both fulfilments updated on the afternoon of 26 Oct 2026 (GMT), hours before the status rename went live (about 21:10 GMT). Slant's own docs example shows the same split (order `PRINTING`, fulfilment `AWAITING_SHIPMENT`), gives only one `fulfillment.status` value ("Fulfillment status, for example SHIPPED") and says a fulfilment is "null until the order ships". So Plinth shows `SHIPPED` (`orderDisplayStatus`, OrderFollowUp.swift) only while the order status is a production status (`orderAttentionProductionStatuses`) and `fulfillment.status` (trimmed, any case) is `SHIPPED` or `DELIVERED` (`orderFulfillmentShippedStatuses`); a `DELIVERED` record has never been seen and also shows as Shipped, so the word never goes backwards when the order status catches up to `SHIPPED`. Anything else (no record, a non-string, `AWAITING_SHIPMENT`, an unknown word, or a draft, cancelled, payment-problem or unrecognised order) shows Slant's order status unchanged. This is display and read-only advice only: the list and detail status (with a hover hint and a caption: “Slant’s shipping record says Shipped, but Slant hasn’t yet updated this order’s status from Printing.”), the Status column's sort, search, Tracking for Your Shop, Needs Attention (no Late or Not shipped), production progress (hidden), Report a Problem's types and message (which quotes the record's own word: "Status: Printing · Shipping record: Shipped"), the cancel review's wording ("Request Refund", “Slant probably can’t stop the delivery. Slant decides whether to cancel it and what to refund.”) and the order watch (below). Whether Cancel is offered, the review sheet's Pay/Cancel gate (`orderConfirmReviewGate`, which takes the order and reads its raw status), the pay and cancel re-checks, the unknown-outcome lock's recorded status, pay outcomes, Pay Several Drafts and the Spending Report use Slant's raw `status`. `GET /orders?status=` filters by the order status, so such orders are listed under Printing or Submitted, not Shipped; the Orders list (under Shipped, and under Printing or Submitted while a loaded order with that status lags), its filtered-empty text and, for a Shipped filter, the Spending Report's scope note say so.
  - The cancel re-check (`orderConfirmRecheck`, and the Workbench's guided `DELETE /orders/{id}` through `workbenchCancelShippingDetailsMessage`) also stops with “This order’s shipping record or tracking changed. Review it again.” when `fulfillment.status` or the tracking numbers (compared as a sorted list) differ between the order shown in the review and the order re-fetched just before sending, before the lock is recorded. It only adds a stop, and never applies to a pay.
  - `SUBMITTED` was first seen on 26 Oct 2026 for an order the owner had just paid (Slant charged it). ## Webhooks

- Headers: `X-Webhook-Timestamp` (**milliseconds**, comparable with `Date.now()`), `X-Webhook-Signature-256` (example `sha256=…`).
- Dead webhook **batch resend** (`POST …/webhook/resend`): capped at **25** per call. Response `data` fields (docs): `attempted`, `delivered`, `failed`, `expired`, `remaining`, `results[]`. Keep calling while `remaining` is above zero.
- **Retry policy** (docs, read 28 Oct 2026): a failed delivery is stored and retried automatically once a minute for up to 10 attempts, then waits for a manual resend; stored webhooks are kept 30 days. A 4xx from your endpoint (except 408 and 429) is a rejection: stored at once with no automatic retries (`retryable: false`). Timeouts, connection failures and 5xx are retried. A manual resend is one attempt and doesn't re-enter the automatic loop; it delivers the stored payload unchanged, signed with a fresh timestamp. Settings lists these under **Recent deliveries**.
- **Single resend** (`POST …/webhook/{webhookId}/resend`) result fields (docs example): `id`, `eventType`, `success`, `status`, `expired`, `alreadyDelivered`, `error`. Plinth shows the result in words (delivered, your endpoint's HTTP status and error, expired, already delivered), then reloads the list.
- **Stored webhooks** (`GET …/webhook`, the last 30 days, delivered ones included): rows carry `id`, `eventType`, `status` (`retrying` / `failed` / `delivered` / `expired`), `lastStatus`, `lastError`, `lastAttemptAt`, `attempts`, `retryable`, `expired`, `succeededAt`. The docs (9 Nov 2026 bundle) also list `service`, `webhookURL` (the last attempt's URL; a changed platform URL takes later attempts), `payload` (the body as sent; a resend delivers it unchanged with a fresh timestamp) and `createdAt` (the first failure, which starts the 30-day window); unverified live. Plinth never shows or logs `payload`. Plinth titles each row by its event and captions it with the status, last reply and time; Try Again (and Resend All) aren't offered for delivered or expired rows. `retryable: false` only stops Slant's automatic retries, so a manual resend stays available.
- **Platform edits** (`PATCH /platforms/{platformId}`) send only the fields the seller changed; a cleared description or webhook URL is sent as `""`. The shop address is checked for https only when it is being changed, so a platform made on the dashboard with an http:// address can still be renamed.
- **Test webhook** (`POST …/webhook/dummy`): inspect `data.success` / `data.response.status`; `data.response.error` is present instead of status when the request failed outright (e.g. DNS failure or timeout).
- Docs (9 Nov 2026 bundle): deliveries carry `User-Agent: Slant3D-Webhook/1.0`. Catalogue events (`component.created`, `component.updated`, `component.deleted`, `filament.updated`) go to every platform with a webhook URL, carry no order data, are never retried and never become stored webhooks. The test webhook's payload carries `dummy: true` and nothing is stored; its envelope `success` means the request was attempted, and `data.success` means your endpoint answered 2xx. `POST /slant/webhook` validates a custom event and delivers it asynchronously to the platform's webhook URL exactly as a real event (no `dummy` flag): a 200 means delivery started, and a failed delivery becomes a stored webhook.
- `webhookSecret` is **not settable on create** (auto-generated). Set your own via `PATCH /platforms/{platformId}` (32–256 characters, printable ASCII 0x21–0x7E, used exactly as sent) or regenerate with `PATCH …/webhook-secret`. Either way the old secret stops at once: the live OpenAPI (28 Oct 2026) says there is no overlap window where both are accepted. Live `GET /platforms` returns `webhookSecret` in full, so Plinth's cached row always has a value to show; after a rotate, or a `PATCH` that sets `webhookSecret` (Settings or the Workbench), whose outcome is unclear (a timeout, transport error, 5xx, 408/409 or unreadable reply), or a rotate whose reply carries no readable secret, Plinth clears that platform's cached secret, hides Show and Copy with a note that it may have changed, and offers **Refresh Platform** (one read-only `GET /platforms/{platformId}`; a reload of the platform list also clears the note). Nothing is sent again.
- **Payload** (spec and docs disagree; Plinth parses none of it, since webhooks go to the seller's own server): the docs' event table lists only `order.shipped` and the catalog events (`component.created`/`updated`/`deleted`, `filament.updated`), while the spec's `WebhookPayload.event_type` enum lists about a dozen more (`order.created`, `order.updated`, `order.cancelled`, `order.delivered`, `order.error`, `payment.*`, `customer.updated`, `file.updated` and others); the docs call the payload `timestamp` "ISO format" but their sample and the spec use a millisecond string; and the docs' sample body has a `signature` field that the spec lacks (the signature travels in `X-Webhook-Signature-256`).
- **Signature recipe** (verbatim from the docs SPA's `verifyWebhookSignature`, unchanged in `assets/index-C5Wnw4hq.js`, read 12 Nov 2026). `timestamp` is the `X-Webhook-Timestamp` header exactly as sent (Unix milliseconds) and `payload` is the exact raw body bytes received, not re-serialised JSON; Plinth's in-app recipe and the bundled spec's `x-agent-hints` say so too:

```javascript
function verifyWebhookSignature(payload, timestamp, signature, secret) {
  const expectedSignature = signature.replace('sha256=', '');
  
  // Reconstruct the signed payload (timestamp + body)
  const signedPayload = `${timestamp}.${payload}`;
  
  // Generate signature using your webhook secret
  const computedSignature = crypto
    .createHmac('sha256', secret)
    .update(signedPayload, 'utf8')
    .digest('hex');
  
  // Compare signatures securely
  const isValid = crypto.timingSafeEqual(
    Buffer.from(expectedSignature, 'hex'),
    Buffer.from(computedSignature, 'hex')
  );
  
  // Check timestamp freshness (reject if older than 5 minutes)
  const age = Date.now() - parseInt(timestamp);
  const isFresh = age < 5 * 60 * 1000;
  
  return isValid && isFresh;
}
```

Secret is the platform `webhookSecret` (trim before use; used exactly as submitted).

## Keeping up with Slant's API

Slant publishes no changelog, RSS feed or API version header, and `info.version` stayed `2.0.0` when the order statuses changed without notice on 26 Oct 2026 (researched 28 Oct 2026). The nearest things are the blog's service-updates category at slant3d.com/blog, the public `/health/status` and the docs site's status page built on it (`/health`), and the docs' **Technical Support** section, which lists support@slant3d.com and dev4@slant3d.com (docs bundles of 29 Oct and 9 Nov 2026). So Plinth keeps its own record:

- `Sources/Plinth/Resources/slant-openapi-upstream.json` is a byte-for-byte copy of Slant's live spec as last reviewed (12 Nov 2026, sha256 `22fbd3c0…`, `ETag: W/"1e459-1a1c1d54d00"`, `Last-Modified: Mon, 09 Nov 2026 19:42:24 GMT`; the revision before it, reviewed 28 Oct 2026, was `Last-Modified: Mon, 26 Oct 2026 21:09:58 GMT`, and the only difference is `POST /files/openScad`'s description, 5 → 100 generations per hour; Slant answers `If-None-Match` / `If-Modified-Since` with 304). It is bundled with `openapi.json`. Never hand-edit it.
- `openapi.json` is that spec plus Plinth's patches. Every patch carries `x-plinth-source: docs` or `live` on the changed operation, parameter, property or schema (or an ancestor), except text appended to Slant's own non-empty `description`; a description Slant doesn't have is a patch and carries a tag. Put the tag on the nearest node that holds the fact, so a live fact never sits under a `docs` tag, and never directly inside a name map (`paths`, `properties`, `schemas`, `responses` and the like), where it would read as one of the map's names. Keep Plinth's own behaviour out of Slant's text: it belongs in this file. Edit it only with a Python round trip that leaves an untouched file byte-identical: `json.dumps(obj, indent=2, ensure_ascii=False) + '\n'`. Tests check that both files load, that `openapi.json` keeps every operation in the snapshot, that no source tag sits at the root or directly inside a name map (`OpenAPISnapshotTests`), and that the script's key lists match `SlantAPIChanges.swift` and its `--self-test` passes (`SlantAPIScriptParityTests`).
- `python3 -I scripts/check-slant-api.py` (standard library only, no key) fetches the live spec (https only, no redirects, ≤ 2 MB, 30 s timeout), prints its ETag and Last-Modified, and compares it with the snapshot as parsed JSON: operations added or removed, then contract changes (parameters, enums, `required`, types, properties) per operation and per schema, apart from wording-only changes (`description`, `summary`, `title`, `example(s)`, `externalDocs`: the same keys the app ignores). Unordered lists (`required`, `enum`, `tags`, `type` arrays and every list but `servers` and `prefixItems`) are compared as sets, as the app does. The script also reports changes the app's daily check ignores (`x-` extensions, `info` other than `version`, the top-level `tags` list, parameter order) and says so under the contract changes. It then lists any difference between `openapi.json` and the snapshot that isn't tagged. Exit codes: **0** no change, **1** contract change, **3** wording only, **2** untagged patches (reported only when Slant's side is unchanged), **5** Slant's docs site changed while the spec didn't, **4** couldn't check (network failure, redirect, too large, not JSON, an unreadable docs page, bad arguments); 1 and 3 outrank the docs page's 4 or 5, which outrank 2. Once the spec is read, the script also fetches `https://slant3dapi.com/documentation/introduction` (keyless, https only, no redirects, ≤ 256 KB) and compares its one `<script type="module" src="/assets/index-….js">` with `scripts/slant-docs-bundle.json` (`assets/index-C5Wnw4hq.js`, recorded 12 Nov 2026). The name changes with any deploy of Slant's site, so 5 means "read the docs again". `--update-snapshot` writes the live bytes over the snapshot after printing the diff (and still exits 1 or 3); `--record-docs` writes the live bundle name to the record (refused with `--offline`; still exits with the code it found); `--offline` doesn't check the docs page; `--offline PATH` compares a file instead of fetching; `--self-test` runs built-in fixtures offline and exits 0 or 1. A tag at the root or directly inside a name map, or a tag value other than `docs`/`live`, is itself reported as an untagged patch.
- A keyless check for a removed GET route (9 Nov 2026): Slant checks the key per route, so a keyless GET to a route that exists answers the 401 JSON, while a path no route matches gets Express's HTML 404 (`Cannot GET /api/…`). On 9 Nov 2026 every GET path in the spec answered 401 and `/health/status` 200; `/v1/api/*` and `/v3/api/*` return the docs site's page (no other API version). It can't test a POST-only route such as `POST /files/direct-upload`, because the GET `/files/:publicFileId` route matches first. Plinth reads that HTML 404 as having no Slant message.
- Run it before every release and whenever Plinth's change check reports that Slant's spec changed. On exit 1 or 3, read the diff, run again with `--update-snapshot`, then bring `openapi.json`, Plinth and this file into line until the script exits 0: the untagged-patch list then shows where `openapi.json` still differs from Slant. A removed enum value is exactly how the order statuses changed.
- The app's own check (`SlantAPIChanges.swift`): `GET https://slant3dapi.com/v2/api/openapi.json` is public and keyless, so Plinth sends it without the key (its own ephemeral session, never `APIClient`; no cookies, credentials or redirects; ≤ 2 MB; 30 s; never retried), while a Slant key is set: about a minute after launch if a day has passed since the last attempt, then once a day (Check Now any time). Observed 28 Oct 2026: the reply carries `ETag: W/"1e457-1a17a0c7070"` and `Last-Modified: Mon, 26 Oct 2026 21:09:58 GMT` (the status change), and a conditional request (`If-None-Match` / `If-Modified-Since`) gets 304 with no body; `info.version` stayed `2.0.0` across the status change, so Plinth never relies on it. The comparison ignores wording (`description`, `summary`, `title`, `example(s)`, `externalDocs`), `x-` extensions, `info` apart from `version` and the top-level `tags` list, and treats lists other than `servers` and `prefixItems` as sets. The saved change token is the hash of exactly what is compared, so an ignored edit can't bring back a dismissed notice, and the saved record is tied to the bundled snapshot's hash and `slantAPIComparisonVersion` (`v2:<sha256>`), so a new snapshot or comparison discards it, dismissed status words included. It only informs: nothing Plinth sends, blocks or accepts depends on it.

## Shopify (optional, seller's own store)

Not a Slant API: Plinth talks to the seller's store directly (`ShopifyClient.swift`, `ShopifyImport.swift`, `ShopifyTracking.swift`, `ShopifyOrderMatching.swift`). Requests go only to `https://<handle>.myshopify.com`; custom domains are refused, input is normalised to `handle.myshopify.com` (bare handle, `handle.myshopify.com` or `admin.shopify.com/store/handle`), and redirects are refused.

- **Auth:** a Dev Dashboard app's client ID and secret, exchanged with `POST https://<shop>/admin/oauth/access_token` (form body `grant_type=client_credentials&client_id=…&client_secret=…`); the token is kept in memory only, for `expires_in` (86,400 s if absent, clamped to 60 s–48 h, renewed 60 s early; a read that gets a 401 fetches a new token once, and a mutation renews a token with under 5 minutes left). Or a legacy `shpat_` Admin API token from a custom app made in the store admin, sent as `X-Shopify-Access-Token`. Credentials are in the Keychain (service `Plinth`, account `shopify-credentials`): the login keychain, since Plinth doesn't use the data protection keychain, so the item is protected by that keychain's lock and its access list; the `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` attribute Plinth passes doesn't apply there (Apple TN3137), so this isn't a "this device only" item. The shop address is in preferences (`shopifyShopDomain`). Scopes: `read_orders` (or `write_orders`) to import, and also to send tracking (Send Tracking finds and reads each order first); `write_merchant_managed_fulfillment_orders` (or the assigned/third-party fulfilment-order write scopes, `fulfillmentCreate`'s documented requirement) to send tracking. They are read from the token reply's `scope` or `currentAppInstallation.accessScopes` and remembered for the connection, except that Send Tracking's check reads them again whenever the remembered ones can't fulfil, fetching a new Dev Dashboard token first (a token's `scope` is fixed when it is issued), and a successful Test Connection replaces them with the live ones (dropping a Dev Dashboard token issued without one of them). So adding the fulfilment scope takes effect on Check Again, without quitting. Whether a token issued before a scope was approved carries it is undocumented; Plinth never relies on it.
- **Endpoint:** Admin GraphQL `POST https://<shop>/admin/api/2026-10/graphql.json`. Operations by name: queries `StudioShop` (Test Connection: shop name, `myshopifyDomain`, `plan { publicDisplayName partnerDevelopment }`, scopes), `StudioScopes`, `StudioImportOrders`, `StudioFindOrder`, `StudioFulfilmentCheck`; mutation `StudioSendTracking` (`fulfillmentCreate`). 30 s request timeout, replies capped at 4 MB, ephemeral session, redirects refused (a 3xx is the reply; pinned for the token request and a mutation by a stubbed-transport test, `ShopifyClientTransportTests`). Any top-level GraphQL error fails the request. Protected customer data is recognised by Shopify's object-level wording ("This app is not approved to access the Customer object", sometimes with `ACCESS_DENIED`) and its field-level wording ("This app is not approved to use the name field", no code, with the rest of `data` still filled). HTTP 403 on the GraphQL Admin API means the store is marked as fraudulent or (27 Oct 2026 changelog) the request came from outside the app's IP allowlist, never a missing scope (that is a 200 with `ACCESS_DENIED`), and Plinth's message says so.
- **Throttling:** Plinth tracks `extensions.cost.throttleStatus` and waits before a request when the bucket is short. Shopify documents GraphQL Admin throttling as a 200 with the `THROTTLED` code (it doesn't use 429 for that; 429 remains for some resource-based limits), and Plinth handles both: throttled (`Retry-After` honoured, capped at 30 s); reads are retried at most 3 times, each wait ≤ 30 s. Mutations are sent once and never retried (`fulfillmentCreate` takes no idempotency key in 2026-10 or 2027-01).
- **Mutation replies with `errors`** (`shopifyMutationErrorReplyMayHaveRun`): Shopify says other error codes than the four it lists may appear, so a `fulfillmentCreate` reply carrying top-level `errors` is a definite refusal only when it clearly is: `THROTTLED` (checked before running) is refused; any `data` object means execution started, so the outcome is unknown; an error without a code, or `INTERNAL_SERVER_ERROR`, is unknown; `ACCESS_DENIED`, `SHOP_INACTIVE` and `MAX_COST_EXCEEDED` (every code one of these) without a `data` object are refused; any other code is refused only when the `data` key is absent altogether (GraphQL leaves it out when a request fails validation, before execution) and unknown with `data: null`. Unknown stops the run like any other unconfirmed send.
- **Fetch from Shopify** (Import Orders): `StudioImportOrders` with `query: "financial_status:paid fulfillment_status:unfulfilled status:open created_at:>=<60 days ago, UTC>"`, oldest first, 8 orders per page (estimated cost 620), at most 250 orders and 30 line items each (an order with more is left out, to import from CSV; when every fetched order is left out, the error names them rather than saying there were none). Any early stop fails the whole fetch rather than showing a partial list. Read: order `name` (the `sourceOrderId`, such as `#1001`), email, cancellation and statuses, the shipping address (no phone), line items (`id`, `name`, `sku`, `quantity`, `currentQuantity`, `unfulfilledQuantity`, visible `customAttributes` as personalisation) and `shopMoney` sale amounts. The result goes into the unchanged import sheet; nothing is sent to Slant until the seller confirms.
  - `fulfillment_status:unfulfilled` also matches partially fulfilled orders (Shopify's REST Order reference: "unfulfilled: Returns orders with fulfillment_status of null or partial"; the GraphQL search uses the same values). So each line's units are `min(currentQuantity, unfulfilledQuantity)` (`shopifyImportLineUnits`: units ordered less those refunded or removed, capped by the units not yet fulfilled; lines at 0 are left out), and `sourceItems` records only those, matching Send Tracking's `remainingQuantity`. Shopify's docs don't say whether `unfulfilledQuantity` leaves out removed units; the minimum is safe either way.
  - An order whose `displayFulfillmentStatus` is `PARTIALLY_FULFILLED`, `IN_PROGRESS` or `PENDING_FULFILLMENT` (sent to a fulfilment service) or `FULFILLMENT_NOT_REQUIRED` (2026-10: nothing left to fulfil), or a Shopify CSV export row whose Fulfillment Status is `partial` (the REST value; the CSV export's exact word is unverified), gets an "already handled" reason and starts unticked (`orderImportAlreadyHandledReason`); the CSV wording adds that the export lists every item, because CSV quantities are the whole order's.
  - `financial_status:paid` leaves out `partially_refunded` (and `partially_paid`) orders, so an order with one item refunded and the rest still to make isn't fetched (the cautious direction; the sheet's help and notice say to use a CSV export for those). Fetching them too is an owner decision.
- **Draft metadata:** `sourceShop` (fetched orders) and `sourceItems`, compact JSON such as `[{"lineItem":"123","quantity":2}]` with each entry keyed by the line item's numeric ID, else its SKU (never its name, which can carry a buyer's text); written only when every included item has one, with at most 60 entries and 1,000 characters (read back up to 2,000).
- **Send Tracking to Shopify…:** for imported Shopify orders with Slant tracking (≤ 50), never a cancelled Slant order (`orderStatusIsCancelled` on Slant's raw status, any spelling: Slant's Cancel also cancels the order's fulfilment). A read-only check first (`StudioFindOrder` by exact `name`, then `StudioFulfilmentCheck`: cancellation, existing fulfilments and tracking numbers, and `fulfillmentOrders(first: 5, displayable: true)` with `pageInfo`, each with ≤ 30 lines; `displayable` leaves out fulfilment orders closed after being combined or moved, which can't be fulfilled). More than 5 fulfilment orders, or more than 30 lines in any read one, blocks the order. Shopify splits orders into several fulfilment orders by location, shipping rate, delivery promise or delivery method (split shipping becomes the default for qualified checkouts by 1 Jul 2027), so among those supporting `CREATE_FULFILLMENT` the order is sent only when exactly one can take every unit recorded in `sourceItems` on its own; when none or several can, it is blocked ("Shopify splits this order into more than one unfulfilled part…"). The review's "Stays unfulfilled" lists what is left in every fulfilment order read. With none supporting `CREATE_FULFILLMENT`, `FULFILLED` is "already fulfilled" and `FULFILLMENT_NOT_REQUIRED` says nothing is left to fulfil. An order not found by name may be older than the 60 days `read_orders` reaches, and the row says so. A draft whose `sourceShop` is another store is refused without contacting Shopify; one without `sourceShop` (a CSV import) must match the order's shipping name and postcode and is never ticked automatically. Only the units recorded in `sourceItems` are allocated; too few unfulfilled units blocks the order. Each send re-runs the check, then `fulfillmentCreate` with exactly those line items of that one fulfilment order, `trackingInfo` (number(s) and company) and `notifyCustomer` (off by default), one order at a time, 0.5 s apart. Stop, closing the sheet and a change of connected store take effect before the next request to Shopify: checked before each order, again after its re-check and once more inside `mutate`, after its own throttle wait and token fetch, just before `fulfillmentCreate` (`shopifyTrackingShouldStop`); a stop there marks that order and the rest Not sent, and is never counted as a refusal. A send already on its way finishes. The first unknown outcome (408/409, 3xx, 5xx, transport error, unreadable reply, an error reply that may have run, cancelled in flight) stops the run; 3 refusals in a row also stop it, and so does a re-check Shopify couldn't answer (with a message, and Activity records it as unsuccessful). The company is `shopifyTrackingCompanyName` of Slant's carrier (spelling fixes to Shopify's 2026-10 list only: "Lasership", "DHL Express" for `DHL_EXPRESS`; a bare "DHL", which could be DHL Express, DHL eCommerce or Germany's DHL, is sent as written, never guessed) or of a detected carrier's Shopify name (Swiss Post included; none for a plain La Poste or Japan Post, which Shopify doesn't list); the tracking CSV names the company the same way.
- **Checked against shopify.dev on 12 Nov 2026** (2026-10 reference, 2027-01 release candidate and the changelog): the items above on throttling, partial fulfilment, `unfulfilledQuantity`, `displayable` fulfilment orders, split shipping, `FULFILLMENT_NOT_REQUIRED`, the 403 meanings, field-level protected data, the mutation error codes and the tracking-company names. `read_orders` and the merchant-managed fulfilment-order scopes carry no "Shopify approval required" mark.
- **Unverified:** live query costs (Plinth uses its own estimates); whether protected customer data needs anything beyond the plan for a merchant's own Dev Dashboard app (Shopify staff on its forum said, Jun–Jul 2026, that such apps get Levels 1 and 2 automatically and have no setting for it, so Plinth's message names the Grow plan and the CSV export, not a Dev Dashboard setting); how Basic/Starter plans withhold customer names and addresses from custom apps (Plinth warns when the plan name contains "basic" or "starter" and treats "not approved to access" or "not approved to use the … field" errors as withheld data); whether a token issued before a scope was approved carries it; the CSV export's exact Fulfillment Status word for a partly fulfilled order (`partial` is the REST value); whether Slant keeps tracking numbers on an order it cancelled; and whether Slant keeps a 1,000-character `sourceItems` string intact (Slant documents no metadata value length).

## Design tools (optional, seller's own keys)

Not Slant APIs. Design an Accessory, Generate a Replica and Review for Printing call Anthropic, Meshy or Tripo with the seller's own keys, from Keychain service `Plinth`, accounts `anthropic-api-key`, `meshy-api-key` and `tripo-api-key` (in the login keychain, protected by its lock and the item's access list: `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` has no effect there, per Apple TN3137). Each key goes only to its own API host (`api.anthropic.com`, `api.meshy.ai`, `openapi.tripo3d.ai` or `openapi.tripo3d.com`) and is redacted from errors and Activity (`aiServiceRedacted`, `imageTo3DRedacted`). Photos are prepared by `ImagePreparation.swift` before sending: read by content (JPEG, PNG or HEIC, ≤ 30 MB, ≤ 120 megapixels), turned upright, long edge ≤ 1568 px for Claude or ≤ 2048 px for Meshy/Tripo, and re-encoded as JPEG (≤ 3.75 MB) without EXIF, GPS, XMP or comment segments. Nothing these tools make reaches Slant until the seller uploads a saved copy. **Nothing in this section has been tested live**; the request shapes come from each provider's documentation (read 24 Oct 2026).

### Anthropic Messages

- **Request** (`AnthropicClient.swift`): `POST https://api.anthropic.com/v1/messages`, headers `x-api-key`, `anthropic-version: 2023-06-01`, `anthropic-beta: server-side-fallback-2026-07-01` (the client can add `thinking-display-updates-2026-08-18`, but no caller asks for it), `content-type: application/json` and `accept: text/event-stream`. Body: `model: "claude-opus-5-5"`, `max_tokens`, `stream: true`, a top-level `system` array, `tools` (every one `strict: true`), `tool_choice: {"type": "auto"}` with `disable_parallel_tool_use: true` where tools are sent, `thinking: {"type": "adaptive"}`, `output_config.effort`, `fallbacks: "default"`, optional top-level `cache_control`, then `messages`. Images (base64 `image/jpeg`; `image/png` is also accepted by the builder) come before the text in the first user turn.
  - Design an Accessory: `max_tokens` 48,000, effort `high`, tools `render_scad`, `ask_seller` and `finish_design` (with `eager_input_streaming: true`), 2 cache breakpoints (5-minute `ephemeral` on the system block, plus top-level automatic caching).
  - Design an Accessory's `finish_design` has a required `photo_check` string (Plinth clips it to 600 characters). Each acceptable render whose code declares `fit_test` is rendered a second time locally with `-D fit_test=true`; that render sends nothing. Before each send Plinth counts the pictures in the conversation and stops before exceeding 100.
  - Review for Printing: `max_tokens` 32,000, effort `high` (the one follow-up `medium`), the single tool `propose_plan` (`eager_input_streaming: false`, nullable fields as `anyOf` with `null`), 1 cache breakpoint (5-minute `ephemeral` on the system block, which also covers the tool before it).
  - Suggest Accessories (`AccessorySuggestions.swift`): `max_tokens` 16,000, effort `medium`, the single tool `suggest_accessories` (`eager_input_streaming: true`; nested objects and arrays, string enums for `confidence`, `fit` and `method`, every property required and `additionalProperties: false`), 1 cache breakpoint (5-minute `ephemeral` on the system block). One fresh single-turn conversation per press: the photos, then text with the optional What is it? hint and, for More Ideas, the titles to avoid. No follow-up or nudge.
  - Save & Test: `max_tokens` 256, effort `low`, no tools or system prompt, the text “Reply with the single word OK.”
  - At most 4 cache breakpoints (checked before sending); the 1-hour TTL is supported but unused.
- **Transport:** ephemeral session (no cookies, cache or credential storage), redirects refused, 300 s idle and 3,600 s total timeout, request body and streamed reply each ≤ 32 MiB, error bodies ≤ 256 KiB. Never retried. The only automatic extra requests are Review for Printing's one follow-up (when the reply has no usable `propose_plan` call) and Design an Accessory's one nudge (when Claude answers without a tool call); **Try Again** in the accessory sheet is an explicit, billed resend.
- **Replies:** history keeps a reply (`.assistant(message)`) only when `canJoinHistory`: `stop_reason` `end_turn`, `tool_use`, `stop_sequence` or `pause_turn`. A `refusal` discards everything written and quotes `stop_details.explanation` (≤ 400 characters); `max_tokens`, `model_context_window_exceeded` and other early stops can't join history. Tools run only on `tool_use`, and a call whose input fails Plinth's checks is answered with an error result, never run. Plinth reads `fallback` content blocks (`from.model`, `to.model`), `usage.iterations[]` (per-iteration `type`, `model` and tokens, including the 5m/1h `cache_creation` split) and `stop_details`; after a mid-reply switch, only the text before the switch joins history.
- **Price** (`anthropicEstimatedCost`, per million tokens): Claude Opus 5.5 $4 input, $20 output, $0.20 cache read, $5 cache write (5 minutes) and $8 (1 hour); each `usage.iterations` entry is priced at its own model's rate (Opus 5 and Opus 4.8 at $5/$25/$0.50/$6.25/$10). Usage Plinth can't price shows as “at least $X”.
- **Forecasts** (shown before sending; Anthropic's invoice is what counts): Design an Accessory assumes about 3.5 characters per token, one image token per 750 pixels, 8,000 output tokens and 4,000 history tokens per reply, and 4 renders of 512 px per later reply, all input written to the 5-minute cache and read back; it shows a typical design (5 replies) and the maximum (10). Suggest Accessories assumes about 3.5 characters per token, one image token per 750 pixels and everything at the plain input price (its prompt is probably below the minimum cacheable length), with 3,000 output tokens at the low end and the full 16,000 at the high end. Review for Printing assumes about 3 characters per token, 784 tokens per 768 px picture (28 px patches), and 3,000–16,000 output tokens, with the high end adding the one follow-up (8,000 output).
- **Unverified:** the streamed shapes of `stop_details`, `usage.iterations` and `fallback`; whether strict tools with `eager_input_streaming` are accepted; whether the `propose_plan` schema's `anyOf` nullable fields are accepted under `strict`; whether the `suggest_accessories` schema (three levels of nesting with enums) is accepted under `strict`; the context-window stop reason's name (`model_context_window_exceeded`); and the cost forecasts' token assumptions.

### Meshy

`MeshyClient.swift`. Base `https://api.meshy.ai/openapi`, header `Authorization: Bearer msy_…`, JSON bodies, 30 s (GET) / 60 s (POST) timeouts. Every create answers 202 `{"result": "<task id>"}` and is sent once (Meshy has no idempotency key; a 4xx means no task was created).

- **Image to 3D:** `POST /openapi/v1/image-to-3d` with `image_url` (a `data:` URI, ≤ 20 MB), `ai_model: "meshy-7.1"` (pinned), `should_texture: false`, `should_remesh: false` (Meshy's highest quality; without remeshing nothing caps the triangle count, since `decimation_mode`, `topology` and `target_polycount` apply only when remeshing), `image_enhancement: false` (Meshy says enhancement redraws the photo), `geometry_resolution: "2k"` only with Higher detail (Ultra, +5 credits; `4k` is single-image only and isn't used) and `target_formats: ["stl"]` (or `"3mf"`); Generate a Replica also sends `auto_size: true` and `origin_at: "bottom"`. Read with `GET /openapi/v1/image-to-3d/{id}` (`status` PENDING, IN_PROGRESS, SUCCEEDED, FAILED, CANCELED, EXPIRED; `progress`; `model_urls`; `task_error`, with `moderation_blocked` reported as refused content). About 20 credits (mesh only); a failed task is refunded.
- **Multi-Image to 3D** (two to four photos): `POST /openapi/v1/multi-image-to-3d` with `image_urls` (data URIs, the front first, then the others in slot order) and the same options; read with `GET /openapi/v1/multi-image-to-3d/{id}`. Same price as one photo. Analyze Printability accepts these tasks.
- **Analyze Printability (free):** `POST /openapi/v1/print/analyze` with `input_task_id`, plus `printer_type: "fdm"` and `intended_print_longest_side_mm` (the replica's processed longest side, 0.1 mm) when known; read with `GET /openapi/v1/print/analyze/{id}` (`printability.status`, error and warning counts, watertight/holes/non-manifold/degenerate metrics, thin walls).
- **Repair Printability (about 10 credits) then Convert (1 credit):** `POST /openapi/v1/print/repair` (same body), then `POST /openapi/v1/convert` with `target_formats` and `input_task_id`; only after a 400/422 refusal does Plinth resend Convert once with the repair's own GLB link as `model_url`. Implemented (`runMeshyRepair`), but no screen uses it yet.
- **Balance:** `GET /openapi/v1/balance` → `balance` (Save & Test and Check Balance).
- **Errors:** 402 = not enough credits or the Free plan (which has no API access); 429 = rate or concurrency limit, with `Retry-After` on the rate limit. Running tasks' `Retry-After` is used as the poll interval (2–30 s). Generated files stay on `assets.meshy.ai` for 3 days.
- **Unverified:** whether Convert accepts a repair task's ID; the STL's units and up axis (Plinth always rescales to the typed size and offers As Made / Turned Upright); how many triangles an unremeshed model has (a download over 128 MB, about 2.68M STL triangles, is a final stop); the multi-image read shape; the API's test key.

### Tripo3D

`TripoClient.swift`. Tripo's v3 API on one of two regional sites with separate keys: `https://openapi.tripo3d.ai/v3` (international) or `https://openapi.tripo3d.com/v3` (China mainland). Header `Authorization: Bearer <key>`; replies are `{"code": 0, "data": {…}}`, and any other code is an error.

- **Upload:** `POST /v3/files`, multipart with the single field `file` (JPEG or PNG, ≤ 20 MB) → `data.file_token`. Free; any failure counts as not sent.
- **Generation:** `POST /v3/generation/image-to-model` with `input` (the file token), `model: "v3.1-20260211"` (pinned), `texture: false`, `pbr: false` and `face_limit` (clamped to 500–1,500,000, or 2,000,000 with detailed geometry; 500,000 for a display piece and 100,000 for a functional part, simplified on the Mac) → `data.task_id`. GLB only; 20 credits. Higher detail adds `geometry_quality: "detailed"` (+20 credits).
- **Multiview** (two to four photos): every photo is uploaded first, then one `POST /v3/generation/multiview-to-model` with the same options and `inputs`, an array of one-key objects `{"front"|"left"|"back"|"right": <file_token>}` (front required; left and right are the object's own sides, a convention taken from third-party docs). An upload failure means nothing was created. 20 credits, as for one photo.
- **Tasks:** `GET /v3/tasks/{id}` (`status` queued, running, success, failed, banned, expired, cancelled; `progress`; `output.model_url`).
- **Convert:** `POST /v3/models/convert` with `input` (the generation task) and `format: "STL"` (or `"3MF"`), 5 credits; no `face_limit` is sent, so every face is kept. The client adds `pivot_to_center_bottom: true` only when asked for the origin at the bottom, which makes it a 10-credit conversion; Generate a Replica never asks (Plinth places the model itself), so a replica costs about 25 credits.
- **Balance:** `GET /v3/account/balance` → `data.balance`, `data.frozen`.
- **Errors:** Tripo's `code` is read only on a 2xx or a 4xx other than 408/409; otherwise the HTTP status decides, so an unclear create stays unknown. HTTP 429, code 1007 (rate) or 2000 (concurrency, with `Retry-After`) is rate-limited; 2010 is not enough credits; 1000/1001 are treated as a bad key; a readable 2xx refusal is a refusal.
- **Conversion links:** an `output` link is kept only if it passes the download checks; an STL/3MF extension is preferred, but a link with any other or no extension is accepted and its content decides (ZIP → 3MF, glTF refused, else parsed as STL).
- **Unverified:** the download host; whether `model_url` links expire after about 5 minutes; whether a `face_limit` of 500,000 is honoured; what "left" means to Tripo; a plain file token as a multiview value; the link format.

### Polling and unknown outcomes

`ImageTo3D.swift`. Status reads every 4 s, up to 10 minutes per stage; transient failures (transport, 408, 5xx, unreadable reply) back off as start × 2^n, capped at 60 s, and 5 in a row stop the run. A 429 waits for `Retry-After` (seconds or HTTP date, capped at 120 s; 16 s without one) and doesn't count as a failure. The API session never follows redirects (a 3xx is unknown) and caps JSON replies at 2 MB. A create whose outcome is unknown (408, 409, 3xx, 5xx, transport error, unreadable or oversized reply, cancelled in flight) is recorded in `ImageTo3DConnection.unconfirmedRequests` (memory only, ≤ 10 with an overflow flag, kept through key and service changes until quit); any other 4xx (including 402 and 429) means not sent. A stop after a task exists keeps a resume point (task and conversion IDs), so **Keep Waiting** polls or downloads the same task without a new create.

### Downloads

Generated models are downloaded (`imageTo3DDownloadURLProblem`) only over https, from a named host that isn't `localhost`, `*.local` or `*.localhost` or an IP literal (checked by name; DNS isn't resolved), with no user, password or fragment. Size ≤ 128 MB, checked against `Content-Length` and while reading; empty bodies refused; 15-minute timeout; 403/404 reported as expired. The download session is ephemeral, sends no `Authorization` header or cookies, and checks every redirect against the same rules. Files land in a `Plinth-Generated3D-<UUID>` temporary folder that is removed after processing.

## Catalog notes

- Components: `categoryId`, `price`, `priceUnit`, `dimensions`, `dimensionUnit`, `weight`, `tags`. Categories: `id`, `name`, `slug`, `parentId`. Slant's docs give `priceUnit` as the enum `["USD"]`, a currency, so Plinth shows "$4.50" rather than "$4.50 / USD" (`catalogPriceText`; any other three-letter currency code follows the amount, and other text is shown as "/ unit").
- Check Cost doesn't price a component or stationery item marked `available: false`; it lists it as not available.
- Filaments (docs and spec): `hexValue` is always 6-digit lower-case hex and falls back to `#a1a1a1` when Slant's source value is missing or malformed (Plinth's listing images then say the colour is Slant's stand-in grey); `imageURL` is optional; `available` is omitted when unknown; `profile` is one of OPM, PLA and PETG. The list is a cache refreshed every 30 minutes. Filters (Workbench only): `profile` (exact, any case) and `color` (partial); values within one parameter are ORed (comma-separated or repeated) and separate parameters ANDed; an unsupported profile rejects the whole request with 400 "Unapproved Profile Passed in Filter Options. Current Public Supported List OPM,PLA,PETG".
- Catalog lists come back complete in one reply (29 Oct 2026: all 84 components with `limit=3`, all 39 filaments): `page` and `limit` are ignored, and the envelope carries a top-level `count` (filaments also `lastUpdated`) rather than `pagination`. Plinth reads `data` and sends no paging.
- Component `dimensions` are free text whatever `dimensionUnit` says (see the table below): Plinth shows them as Slant sends them, trimmed, and never adds a unit.
