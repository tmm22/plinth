# Slant 3D V2 API integration reference

Verified 18 October 2026 from [official documentation](https://slant3dapi.com/documentation/introduction) (docs SPA bundle `assets/index-DSzyXtco.js`; `assets/index-BcaZVnjh.js` on 29 Oct 2026), and [official OpenAPI](https://slant3dapi.com/v2/api/openapi.json). The bundled `Sources/SlantStudio/Resources/openapi.json` is the official spec plus supplements marked with `x-slant-studio-source: docs` (from Slant's docs) or `live` (seen in Slant's replies, nearly always to read-only requests); `slant-openapi-upstream.json` beside it is Slant's spec as last reviewed (see [Keeping up with Slant's API](#keeping-up-with-slants-api)).

## Connection and prerequisites

- Production base: `https://slant3dapi.com/v2/api`. Bearer API key in `Authorization`, JSON bodies with `Content-Type: application/json`. Do not send bearer credentials to presigned storage URLs.
- Exception: `POST /slant/webhook` uses `https://slant3dapi.com/v2/slant/webhook`, outside the `/api` prefix (operation-specific server in OpenAPI).
- Rate limit: **100 requests/minute** per API key. Response headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (epoch **milliseconds**, live 23 and 29 Oct 2026; Slant's docs say "Unix timestamp" and their sample multiplies it by 1000; `rateLimitResetDate` also accepts epoch seconds, reads a small number as seconds from now, and ignores negative, unparseable or more-than-a-day-away values), `X-RateLimit-Role`. The public `/health/status`, `GET /apiKey` and the authentication layer's 401s send none of these, so Studio keeps the last known values whenever a response carries no rate-limit headers. OpenSCAD: **5 generations/hour**, one in flight. Up to three API keys and five enabled platforms. No public sandbox.
  - What `X-RateLimit-Reset` marks is unresolved (read-only GETs). Some replies give a fixed time up to about 60 s ahead that stays put while `X-RateLimit-Remaining` falls (`1800000685873` was 60 s after the request on 23 Oct 2026; on 29 Oct 2026 one value held for 14 s while Remaining fell by ten). Others give a time only a few seconds ahead that moves later with each request while `X-RateLimit-Remaining` stays level or goes back up by one (29 Oct 2026), as a sliding 60 s window would. Either way, waiting until Reset may free only one request, so every paced batch checks the figures again before its next call.
  - `GET /usage` reports `rateLimitConfig.blockDurationMs: 60000`; whether a 429 blocks the key for that long, and which headers a 429 carries, are unverified. So after a 429, Compare estimates, Check Cost, Import Orders, Pay Several Drafts and Load the Whole Period send nothing more for at least 60 s (`comparisonRateLimitedUntil`), whatever Reset says. The order watch has its own backoff, and Personalise from Template's hourly OpenSCAD limit is separate (below).
- Most workflows require an owned platform. Drafting does not charge; processing charges and starts production. Key creation/listing (`/apiKey`) is session-only (dashboard): with an API key, `GET /apiKey` is 401 `{"error":"Unauthorized","message":"Please log in to access this resource"}` (29 Oct 2026).
- Requests to the Slant API carry `User-Agent: SlantStudio/<CFBundleShortVersionString, else "dev"> (macOS <version>)`; presigned storage PUTs and file downloads don't. Query values are percent-encoded including `+` (`%2B`), because Slant's server reads a bare `+` as a space (`slantAPIURL`).
- Errors (read-only GETs, 28–29 Oct 2026): `{"success":false,"error":{"message":"…","statusCode":400}}` (not the spec's `ErrorResponse`, whose `error` is a string), and no request-ID header is sent. The authentication layer answers differently: an unauthenticated 401 is `{"error":"Unauthorized","message":"Bearer token required in Authorization header","format":…}`, an invalid key gets the same shape with "Invalid API key", and an endpoint above the key's role is 403 `{"error":"Forbidden","message":"Minimum role required: admin","requiredRole":…,"currentRole":…}`. `GET /orders` 400s name the parameter, such as "Invalid limit passed on query: 201. Limit maximum is 200". `shortAPIMessage` reads `message`, then `error.message`, then `error`. Quoted messages pass `apiMessageRedactingCredentials`, which masks bearer values and Slant keys in either form, `sl-…` (the docs, the `/usage` key prefix and live keys) or `sl_…` (the spec's `ApiKeyAuth`). The spec also documents 401 for "Order belongs to another creator" / "File belongs to another creator", so Studio says to reconnect only when a 401 has no message or one about the token, key or authorisation, and otherwise quotes Slant ("Slant refused this request. …"). A 409 is worded as a conflict (refresh before trying again), since Studio treats it as an unknown outcome for writes. A 2xx whose envelope says `success: false` stays an unknown outcome; its message is quoted. A numeric `Retry-After` (not documented by Slant) gives the wait in the 429 copy; otherwise `X-RateLimit-Reset`.

## Upload and manufacture

1. `POST /files/direct-upload` with `name`, `platformId` required; `ownerId` optional; `type` optional `stl` | `3mf` | `obj` (default `stl`), as for `POST /files`. The guided Models upload sends the library file unchanged in its original format, omitting `type` for STL and sending `obj` or `3mf` otherwise. OBJ/3MF preview, unit conversion and **Save STL copy** are local only; Studio never sends its converted copy unless you upload it as its own model.
   - **Slant converts 3MF uploads to STL** (live, 29 Oct 2026): every file record reads `type: "stl"` with a `.stl` storage key, including two 3MF uploads (21 and 23 Oct 2026), whose stored bytes (a ranged GET of `fileURL`) begin `Binary STL converted from 3MF by file-service`. Slant's docs list obj, 3mf and stl in their File Structure and say of `fileURL` "Only the STL file can be downloaded", which fits; the spec's own `File.type` (`["stl"]`, "currently only STL supported") is right for records. The bundled `File.type` keeps `stl`, `obj` and `3mf` (now tagged `live` with this note) because `confirm-upload` sends that schema back as `filePlaceholder`, and the Workbench validates it. So **Download into Library** of a 3MF upload gets Slant's STL conversion (`cloudDownloadExtension` reads `stl`), without the 3MF's units or Source and licence details. Unverified: whether OBJ uploads are converted the same way and what an OBJ record's `fileURL` serves, and how the conversion treats 3MF units other than millimetres or files that place several objects (that decides what Slant prints).
   - **Slant files an upload under its name** (live, 30 Oct 2026). Slant's docs say a file's `name` is "Sanitized before storing. Unique to ownerId" (the spec doesn't); with no `ownerId` sent, every file's `ownerId` equals its `creatorId`, so that means unique across the account. Two uploads named “Studio name test” (the same small STL) showed what it does: the second `POST /files/direct-upload` returned the same `filePlaceholder` as the first (the same internal `id` and `publicFileServiceId`) and the same storage key (`…/<id>/Studio name test.stl`), before any bytes were sent; both confirms returned the same `publicFileServiceId`, and `GET /files` lists one record. So an upload whose name matches one of the owner's files reuses that file's record, and its PUT writes over the same storage object: every draft, and possibly every order, that uses that `publicFileServiceId` then prints the new contents. The two test files were identical, so the replacement is inferred from the shared key, not observed. Unverified: whether the match ignores case or the extension, whether a paid order's print is affected, and whether `POST /files` (Upload from URL) does the same, which is likely.
   - What Studio does about it. **Upload Model**, **Upload Again…** and **Upload from URL…** first compare the name with your whole Slant file list (`checkUploadName`, `slantUploadNameConflict`). Slant's rule is unknown, so the comparison errs towards a match (`slantUploadNameKey`): trimmed, runs of spacing collapsed, any case, and a trailing `.stl`, `.obj` or `.3mf` ignored. A model linked to a listed cloud file is checked under that file's name, so its own earlier upload is the one offered (`slantUploadNameCheckResult`). Before every such upload Studio reads every page of `GET /files` afresh: read-only, no `platformId` (names are unique per owner), pages of 100, 0.6 s apart, at most 50 pages. That read only feeds the check and the guard below; it doesn't change the Models file list. It stops before each page while `X-RateLimit-Remaining` is at or below the order watch's reserve of 20 (until `X-RateLimit-Reset`, or for a minute when no reset time came back), and after a 429 no check reads again until the latest of `X-RateLimit-Reset`, a numeric `Retry-After` and 60 s from now (`slantUploadNameCheckRateLimitStop`, `comparisonRateLimitedUntil`). If the read fails, stops for the rate limit or returns a page without file names, nothing is uploaded and the message says to upload again (Upload from URL shows it in its sheet); the alert offers no **Try Again**, and the check is never retried. More than 5,000 files is a final refusal, with its own message. When a file has the name, a confirmation titled “This name is already in your Slant files” says “A file named “X” is already in your Slant files. Uploading with this name replaces that file for every draft that uses it, and possibly for orders not yet printed.”, adding when the match is this model's own earlier upload (or may be an upload Slant didn't confirm), and offers **Upload as “X 2”** (the first “X N” that no file just read, or already loaded, has, with a `.stl`/`.obj`/`.3mf` ending kept last, `slantUploadUniqueName`), **Replace File** and **Cancel**, the default (Escape); no keyboard shortcut sends. **Upload Again…** shows one dialog: that one, or, when the name is free, a single confirmation that it uploads as a new file. Import Orders' personalised uploads end in a short random token instead (eight hex characters from a fresh UUID, such as “Etsy order 123 personalised 1 of 2 · 7f3a9c21”), so no two of them share a name in a batch or a session, and they need no check. When a confirmed upload returns a `publicFileServiceId` that another library model is already linked to, the link stays only on the model just uploaded, because that cloud file now holds its contents (`modelsLosingLinkAfterUpload`; after Upload from URL, which links no model, no library model keeps it).
   - **The pre-PUT guard** (`APIClient.upload`'s `checkPlaceholder`). Slant returned the existing file's `filePlaceholder`, with its `publicFileServiceId`, from step 1, before any bytes were sent (above), so Studio checks that `publicFileServiceId` before the PUT and stops with nothing sent when it names a file that must be kept (`uploadPlaceholderProtectedFile`, `UploadWouldOverwriteExistingFile`): for Models, every file the name check just read or had loaded, less the one the seller chose to replace (`uploadProtectedFiles`); for personalised uploads, the loaded files, every library model's link and the files this batch already uploaded (`batchPersonaliseProtectedFiles`), and such a stop skips only that order, as a refusal. A placeholder without a string `publicFileServiceId` can't be checked and passes. Upload from URL is one `POST /files`, with no placeholder before Slant stores the file, so the guard can't run there.
   - Local preview limits (client-side, `ModelFormats.swift` / `ZipArchive.swift`): 128 MB file and 500,000 triangles for every format. 3MF: at most 128 MB expanded in total, 10,000 ZIP entries, 1,000 model parts, component depth 32 and 100,000 placements (applied to both the triangle-count and the placement pass); entries over 1 MB that expand more than 200:1 are refused, as is any DTD (`<!DOCTYPE`/`<!ENTITY`, checked in UTF-8 and UTF-16 and by the XML parser's declaration callbacks). OBJ: lines up to 64 KB; polygons are ear-clipped on their best-fit plane (convex faces keep the fan from corner 0) within a per-file work budget; a face that crosses itself, or one over the budget, is previewed as a fan and blocks STL and scaled copies of that file.
2. PUT raw bytes to `data.presignedUrl` without Authorization; retain `data.filePlaceholder` unchanged.
3. `POST /files/confirm-upload` with `{ "filePlaceholder": <exact object> }`. Identifier is `publicFileServiceId`. Prefer `metrics` over deprecated `STLMetrics`.
   - Docs (read 28 Oct 2026): uploads up to 250 MB and the 220 mm cube; at most 500 uploads a day per platform (upload tokens per platform reset every 24 hours); confirm every upload, and "upload and confirm files in batches of 2 to avoid issues with file analysis". Studio uploads one file at a time. The Models upload words a failure by its step (`uploadFailureMessage`): no usable link from step 1 or a refused or expired storage link in step 2 (a storage 403 isn't about the API key) means nothing was stored, unless it was a Replace File (below); after step 3 anything but a definite refusal (timeout, transport error, 5xx, 408/409, an unreadable or `success: false` reply, or a 2xx without a file ID) leaves the file possibly on Slant, so Models suggests Refresh and asks before uploading again (a standard key can't delete files). After **Replace File**, which reuses the existing file's record and storage key, a failure once the PUT may have started (any step-2 failure, or any step-3 failure, even a definite refusal, because the bytes may already be stored) is worded as possibly having left that file holding part of the new model for every draft that uses it (`uploadReplacementMayBePartial`, `uploadReplacementPartialMessage`): every library model linked to that file, this one included, loses its link, the selected file and estimate are cleared when they point at it, and the message names the models to upload again. Upload from URL's **Replace File** does the same after an unclear reply (`uploadFromURLReplaceUnclearMessage`). This is a precaution: whether a failed storage PUT can leave a partial object is unverified. Only a real file ID links the upload, never the name: `publicFileServiceId`, else `publicId`, else `id` only when it is a non-empty string (the docs' `filePlaceholder` example has `"id": 9999`, an internal number). Nothing is retried.
   - A file Slant hasn't measured (no measured `metrics`) offers **Check Again**: one read-only `GET /files/{publicFileId}` per press, merged into that row; nothing checks by itself. Slant can leave a file unmeasured indefinitely: one 3MF upload (23 Oct 2026) still had every `metrics` and `STLMetrics` value `null` apart from `units` on 29 Oct 2026, while the other converted 3MF was measured, so the cause isn't known. Neither the docs (metrics "read null until the file has been analyzed") nor the spec describe a failed analysis. So Model analysis says Slant is analysing only a new upload; once the upload is more than about an hour old it says Slant hasn't measured the model since it was uploaded on that date and suggests uploading the model again (`metricsPendingCaption`, after `metricsPendingStaleAfter`, one hour; with no readable upload date it stays “Analysing…”); that upload goes through the same-name check, where Upload as “X N” keeps the old file and Replace File reuses it. It doesn't say why, or that estimates will fail. Download into Library reads the file's `fileURL` with no Authorization, refuses redirects, writes the chunks URLSession delivers straight to a temporary file and stops above 300 MB (Content-Length or while reading).
   - `metrics.units` (live, 29 Oct 2026, every file listed) gives one unit for all three sizes under `dimensions` (`mm`), beside `weight` (`g`), `volume` (`cm3`), `surfaceArea`, `printTimeEstimate` (`min`) and the support estimates. Studio reads `units.x`/`y`/`z` when present, else `units.dimensions` (`metricUnit`), skips a null or empty unit, and otherwise assumes mm, g, cm³ and minutes.
4. Estimate with `POST /files/{publicFileId}/estimate`. Draft with `platformId`, customer details/address, and items. **Get Estimate** applies Compare estimates' check (`comparisonPrice`): a reply without a usable `total`, or for another `quantity`, is shown as a failure, not an estimate.
   - Request: `{ "options": { "filamentId": <uuid>, "quantity": <int ≥ 1> } }`; both optional (PLA Black, quantity 1). Response `data`: `subtotal` (before surcharges), `total` (estimated print cost, USD), `pricePerUnit`, `quantity`, `totalMaterial`, `estimatedPrintTime`, `bodyChargeCost`, `oversizeSurcharge`. No delivery cost: shipping is priced only by the order draft (`totals.deliveryCost`). The OpenAPI gives no unit for `totalMaterial` or `estimatedPrintTime` and says `subtotal` and `totalMaterial` are for the quantity requested; the docs' example has `subtotal` equal to `pricePerUnit` at quantity 5 and a one-unit `totalMaterial`. Live, 23 Oct 2026, on a converted 3MF (quantity not recorded): `estimatedPrintTime` 6.66 against the file's `printTimeEstimate` of 402 minutes, which is within 1% of 402 ÷ 60, so it may be hours (one observation; undocumented); `subtotal` 7.64 against `pricePerUnit` 9.93 with both surcharges 0, which fits neither reading. So Studio shows the total, price per unit and any non-zero surcharge, and leaves print time and weight to Model analysis (`metrics`, documented as minutes and grams).
   - Observed 25 Oct 2026 (three uploads of a 40×40×20 mm STL, PLA, quantity 1; Studio's strength test): a plain block reported `metrics.bodyCount` 1, `bodyChargeCost` 0, `total` 1.91, `weight` 18.04 g, `printTimeEstimate` 104; the same block with nine closed internal voids (0.25 × 35 × 17 mm) reported `bodyCount` 10, `bodyChargeCost` 3.50 (about $0.39 per extra body), `total` 6.95, weight 29.62 g; the same slots open through the bottom face reported `bodyCount` 1, `bodyChargeCost` 0, `total` 2.43, weight 30.45 g, `printTimeEstimate` 134, `supportAreaEstimate` 78.75 mm² with `supportRequired: false`. So closed voids are billed as bodies, surface-open slots aren't, and the slicer prints walls round the slots. Studio names the charge “Charge for N extra bodies” using the estimated file's own `bodyCount`.
   - Slant's published print-on-demand settings (Slant blog settings graphic, read 25 Oct 2026), not changeable per order or by API (`items[].options.slicerOptions` has no active overrides): 0.2 mm layers, 0.3 mm first layer, 1 mm walls, 25% infill, 50° overhangs, no brims, 0.4 mm nozzle, 220 mm cube, textured bed; uploaded orientation kept unless obviously wrong; supports decided at upload. Unpublished: line width, tolerances and the slicer used.
   - One material and one quantity per call; there is no batch estimate. Estimates are side-effect free and the only POST the error alert's **Try Again** may resend (`StudioStore.RetryAction`: GETs plus the estimate, pinned by `ShellUXTests.testEveryRetryActionIsReadOnlyOrEstimate`); Studio never retries anything automatically.
   - **Compare estimates** (`EstimateComparison.swift`; offered once the model is uploaded and materials are loaded) issues up to 20 of these calls (≤ 4 materials × ≤ 5 quantities), strictly sequentially and at least 0.6 s apart (100 requests/minute). Before each call it stops, keeping completed results, when `X-RateLimit-Remaining` ≤ 10 and `X-RateLimit-Reset` is in the future (without a reset header, a low count is trusted for 60 s), after a 429 (blocked until the latest of `X-RateLimit-Reset`, a numeric `Retry-After` and 60 s from now, at most an hour), on 401/403/404/408/409/5xx or a transport error, after 3 consecutive per-cell failures (400/422 or a response without `total` or with a different `quantity`), or when the selected file, connection or global busy state changes. It does not set the app-wide busy flag. Rate-limit state is updated only from responses that carry `X-RateLimit-*` headers. Quantities are whole numbers from 1 to 10,000 (ambiguous input such as `1,500` is refused). Per unit is computed as `total ÷ quantity`; `total` is after surcharges (`subtotal` is before them), so surcharges are spread across the units. A cell applied with **Use** becomes the current estimate under the same `fileID|filamentID|quantity` context as **Get Estimate**.
   - **Check Cost** (Saved Products, `ProductCostCheck.swift`) sends the same request once per print line of a saved product, with `quantity` = the line's quantity × the units typed (once-per-order lines: the line's quantity alone) and the line's `filamentId`: at most 20 calls, with Compare estimates' spacing, rate-limit stop (≤ 10 remaining, or after a 429) and no retries, stopping after 3 prints in a row fail. It doesn't set the busy flag; it won't start while busy and stops before the next call if another task starts. Components and stationery are priced from the loaded catalog (`price` × quantity, USD only) without a request. Results are session-only; Activity records counts only.
5. Draft response `data` shape (docs): `{ order, items, totals: { printingCost, deliveryCost, totalCost }, customer }`. The docs give `totals` "as numbers" (example 35.53); the order's own `printingCost` and `deliveryCost` are strings in the docs and live. Whether the live draft reply's totals are numbers is unverified, and Studio reads either (`orderStrictAmount`, `decimalAmount`). The docs' draft-reply items also carry `fileURL` (`"Unknown"` for a print), `componentName` and `stationeryName`, which the spec's `OrderItem` lacks.
6. Process with `POST /orders/{publicOrderId}`; cancel with `DELETE` (see refund note below). The pay reply's shape is unverified live: the docs say every order endpoint but Get Order returns the order directly on `data` (their example has `data.status: "SUBMITTED"`), while the spec says `data.order`. Studio reads both (`orderObject`), and the pay outcome rules don't depend on which. OpenSCAD returns raw STL bytes (`application/sla`).

## Delivery address defaults and lookup

The guided order composer defaults the shipping country from the Mac’s Region setting, with delivery details reused from the current session taking priority. Region is an editable default, not physical-location detection.

**Use Current Location** is an optional client-side Apple Core Location and reverse-geocoding flow, not a Slant endpoint. It requests permission only after the button is pressed and offers a suggested street address for review. **Use This Address** replaces shipping fields, clears the old apartment/unit number, and retains name and email. Coordinates are not added to the Slant order payload or activity log. The reviewed address is sent through the normal order-draft request when the user creates the draft.

The app rejects fixes older than 60 seconds or with horizontal uncertainty over 100 metres, and stops lookup after 45 seconds. These are app heuristics, not delivery-address verification. Missing street/country information, lookup errors and denied permission leave manual entry available. See `DeliveryLocation.swift` and the permission descriptions in `scripts/build-app.sh`.

## Orders, fulfillment, cancel / refund

- **Order statuses since 26 Oct 2026** (live OpenAPI and docs, checked with read-only GETs on 28 Oct 2026): `DRAFT` ("Drafted and not yet processed. Nothing has been charged or sent to production"), `SUBMITTED` ("Processed and paid. The order is with us and waiting to print"), `PRINTING` ("In production: printing, finishing and packing"), `SHIPPED` ("Handed to the carrier. Tracking is on fulfillment.trackingNumbers") and `CANCELLED` ("Cancelled before it shipped"). `GET /orders?status=` takes exactly these five (case-insensitive) and refuses any other value with 400 “Invalid status filter”. Orders paid before the change read `PRINTING` on 28 Oct 2026. Studio shows Submitted with the hint “Paid, waiting to print” and Printing with Slant's “In production” description.
  - The earlier 14-value set (`DRAFT`, `PAID`, `QUEUED`, `PROCESSING`, `PRINTING`, `ITEMS_ON_SHELF`, `POST_PROCESSING`, `COMPLETED`, `IN_REVIEW`, `AWAITING_SHIPMENT`, `SHIPPED`, `DELIVERED`, `CANCELED`, `PAYMENT_ERROR`) is no longer returned. Studio keeps those values only to read saved order-watch snapshots and old replies (`orderLegacyStatuses`), never offers them as a filter, and treats Slant's re-labelling of a saved status (to `SUBMITTED` or `PRINTING`, `CANCELED` → `CANCELLED`, `DELIVERED` → `SHIPPED`) as no change.
  - Spelling: the live value is `CANCELLED`; the earlier one was `CANCELED`. Studio accepts both (`orderStatusIsCancelled`) and shows “Cancelled”.
  - **The order status can lag the shipping record** (read-only GETs, 29 Oct 2026): two paid orders read `status: "PRINTING"` while their `fulfillment` was `{status: "SHIPPED", provider: "SHIPPO", deliveryMethod: "INTERNATIONAL", trackingNumbers: [one number], labelPrinted: true, providerStatus: null}`, with both fulfilments updated on the afternoon of 26 Oct 2026 (GMT), hours before the status rename went live (about 21:10 GMT). Slant's own docs example shows the same split (order `PRINTING`, fulfilment `AWAITING_SHIPMENT`), documents no `fulfillment.status` values and says a fulfilment is "null until the order ships". So Studio shows `SHIPPED` (`orderDisplayStatus`, OrderFollowUp.swift) only while the order status is a production status (`orderAttentionProductionStatuses`) and `fulfillment.status` (trimmed, any case) is `SHIPPED` or `DELIVERED` (`orderFulfillmentShippedStatuses`); a `DELIVERED` record has never been seen and also shows as Shipped, so the word never goes backwards when the order status catches up to `SHIPPED`. Anything else (no record, a non-string, `AWAITING_SHIPMENT`, an unknown word, or a draft, cancelled, payment-problem or unrecognised order) shows Slant's order status unchanged. This is display and read-only advice only: the list and detail status (with a hover hint and a caption: “Slant’s shipping record says Shipped, but Slant hasn’t yet updated this order’s status from Printing.”), the Status column's sort, search, Tracking for Your Shop, Needs Attention (no Late or Not shipped), production progress (hidden), Report a Problem's types and message (which quotes the record's own word: "Status: Printing · Shipping record: Shipped"), the cancel review's wording ("Request Refund", “Slant probably can’t stop the delivery. Slant decides whether to cancel it and what to refund.”) and the order watch (below). Whether Cancel is offered, the review sheet's Pay/Cancel gate (`orderConfirmReviewGate`, which takes the order and reads its raw status), the pay and cancel re-checks, the unknown-outcome lock's recorded status, pay outcomes, Pay Several Drafts and the Spending Report use Slant's raw `status`. `GET /orders?status=` filters by the order status, so such orders are listed under Printing or Submitted, not Shipped; the Orders list (under Shipped, and under Printing or Submitted while a loaded order with that status lags), its filtered-empty text and, for a Shipped filter, the Spending Report's scope note say so.
  - The cancel re-check (`orderConfirmRecheck`, and the Workbench's guided `DELETE /orders/{id}` through `workbenchCancelShippingDetailsMessage`) also stops with “This order’s shipping record or tracking changed. Review it again.” when `fulfillment.status` or the tracking numbers (compared as a sorted list) differ between the order shown in the review and the order re-fetched just before sending, before the lock is recorded. It only adds a stop, and never applies to a pay.
  - `SUBMITTED` was first seen on 26 Oct 2026 for an order the owner had just paid (Slant charged it). Studio treats it as placed (Spending Report, Needs attention, Pay Several Drafts, marketplace duplicates) and cancellable; order watch treats moves among Draft, Paid and Submitted as the seller placing the order.
  - **A cancel lock and a lagging status.** A cancel's unknown-outcome lock lifts when a reload shows the order's status changed from the one the cancel was sent from, except a move from a production status (`orderAttentionProductionStatuses`, such as Submitted or Printing) to Shipped or the earlier Delivered (`orderFulfillmentShippedStatuses`); statuses are compared trimmed and in any case (`outcomeResolved`). That move is how Slant's order status catches up with its shipping record, and an order being made ships whether or not a refund was asked for, so it says nothing about whether the cancel (which Slant's docs say "will only refund" once shipped) took effect (owner decision, 30 Oct 2026). The lock then stays until a cancelled status or another change, a confirmed reply, a definite refusal, or quitting: the review says the order has shipped since and to check it in the Slant dashboard (`unknownOutcomeShippedSinceCancelMessage`), and Pay Several Drafts names the locked order (`batchPayLockedMessage`). Unverified (a write): what `DELETE` does to a Submitted, Printing or Shipped order, its success body, and whether a refunded Shipped order stays Shipped.
- **Which platform an order is on** (read-only GETs, 29 Oct 2026; the account has one platform and 6 orders). Slant's docs list no `platformId` or `ownerId` filter for `GET /orders`; the spec lists both. Live, an unknown or malformed `platformId` (a random UUID, `not-a-uuid`) and an unknown `ownerId` were ignored: every order on the account came back, with the same ETag as no filter. Whether the ID of a second platform the account owns would filter is unverified. (`GET /files?platformId=<random UUID>` does filter: count 0.) Every order seen names its platform in `customer.platformId` (spec, docs and live agree) and none has a top-level `platformId`, `ownerId`, `creatorId` or `id`; a draft Studio created with a top-level `platformId` has it stored on the customer.
  - So Studio keeps sending `platformId` on list reads but never relies on it. `orderPlatformMatch` reads an order's `customer.platformId`, then a top-level `platformId`, and gives no answer when the order names neither. It decides only what is **shown or summed**: the Orders list's rows (and so Export Orders…, Review Drafts One by One… and Pay Several Drafts' candidates, which come from them), both Spending Report modes, and the order watch's saved statuses (so another platform's order never reaches the banner, badge or a notification). An order naming another platform is hidden there and one naming none is kept; the Orders list also keeps any order with an unknown pay or cancel outcome, so its Reload Order stays reachable (the Spending Report and the order watch don't, since it isn't this platform's spend or news). Tracking for Your Shop and Check Cost's delivery hint read every loaded order and aren't platform-checked. When rows are hidden, the Orders list says how many orders on other platforms it isn't showing. ## Webhooks

- Headers: `X-Webhook-Timestamp` (**milliseconds**, comparable with `Date.now()`), `X-Webhook-Signature-256` (example `sha256=…`).
- Dead webhook **batch resend** (`POST …/webhook/resend`): capped at **25** per call. Response `data` fields (docs): `attempted`, `delivered`, `failed`, `expired`, `remaining`, `results[]`. Keep calling while `remaining` is above zero.
- **Retry policy** (docs, read 28 Oct 2026): a failed delivery is stored and retried automatically once a minute for up to 10 attempts, then waits for a manual resend; stored webhooks are kept 30 days. A 4xx from your endpoint (except 408 and 429) is a rejection: stored at once with no automatic retries (`retryable: false`). Timeouts, connection failures and 5xx are retried. A manual resend is one attempt and doesn't re-enter the automatic loop; it delivers the stored payload unchanged, signed with a fresh timestamp. Settings lists these under **Recent deliveries**.
- **Single resend** (`POST …/webhook/{webhookId}/resend`) result fields (docs example): `id`, `eventType`, `success`, `status`, `expired`, `alreadyDelivered`, `error`. Studio shows the result in words (delivered, your endpoint's HTTP status and error, expired, already delivered), then reloads the list.
- **Stored webhooks** (`GET …/webhook`, the last 30 days, delivered ones included): rows carry `id`, `eventType`, `status` (`retrying` / `failed` / `delivered` / `expired`), `lastStatus`, `lastError`, `lastAttemptAt`, `attempts`, `retryable`, `expired`, `succeededAt`. Studio titles each row by its event and captions it with the status, last reply and time; Try Again (and Resend All) aren't offered for delivered or expired rows. `retryable: false` only stops Slant's automatic retries, so a manual resend stays available.
- **Platform edits** (`PATCH /platforms/{platformId}`) send only the fields the seller changed; a cleared description or webhook URL is sent as `""`. The shop address is checked for https only when it is being changed, so a platform made on the dashboard with an http:// address can still be renamed.
- **Test webhook** (`POST …/webhook/dummy`): inspect `data.success` / `data.response.status`; `data.response.error` is present instead of status when the request failed outright (e.g. DNS failure or timeout).
- `webhookSecret` is **not settable on create** (auto-generated). Set your own via `PATCH /platforms/{platformId}` (32–256 characters, printable ASCII 0x21–0x7E, used exactly as sent) or regenerate with `PATCH …/webhook-secret`. Either way the old secret stops at once: the live OpenAPI (28 Oct 2026) says there is no overlap window where both are accepted. Live `GET /platforms` returns `webhookSecret` in full, so Studio's cached row always has a value to show; after a rotate, or a `PATCH` that sets `webhookSecret` (Settings or the Workbench), whose outcome is unclear (a timeout, transport error, 5xx, 408/409 or unreadable reply), or a rotate whose reply carries no readable secret, Studio clears that platform's cached secret, hides Show and Copy with a note that it may have changed, and offers **Reload Platform** (one read-only `GET /platforms/{platformId}`; a reload of the platform list also clears the note). Nothing is sent again.
- **Payload** (spec and docs disagree; Studio parses none of it, since webhooks go to the seller's own server): the docs' event table lists only `order.shipped` and the catalog events (`component.created`/`updated`/`deleted`, `filament.updated`), while the spec's `WebhookPayload.event_type` enum lists about a dozen more (`order.created`, `order.updated`, `order.cancelled`, `order.delivered`, `order.error`, `payment.*`, `customer.updated`, `file.updated` and others); the docs call the payload `timestamp` "ISO format" but their sample and the spec use a millisecond string; and the docs' sample body has a `signature` field that the spec lacks (the signature travels in `X-Webhook-Signature-256`).
- **Signature recipe** (verbatim from the docs SPA's `verifyWebhookSignature`, still in `assets/index-BcaZVnjh.js` on 29 Oct 2026). `timestamp` is the `X-Webhook-Timestamp` header exactly as sent (Unix milliseconds) and `payload` is the exact raw body bytes received, not re-serialised JSON; Studio's in-app recipe and the bundled spec's `x-agent-hints` say so too:

```javascript
function verifyWebhookSignature(payload, timestamp, signature, secret) {
  const expectedSignature = signature.replace('sha256=', '');
  
  // Reconstruct the signed payload (timestamp + body)
  const signedPayload = `${timestamp}.${payload}`;
  
  // Generate signature using your webhook secret
  const computedSignature = crypto
    .createHmac('sha256', secret)
    .update(signedPayload, 'utf8')
    .digest('hex');
  
  // Compare signatures securely
  const isValid = crypto.timingSafeEqual(
    Buffer.from(expectedSignature, 'hex'),
    Buffer.from(computedSignature, 'hex')
  );
  
  // Check timestamp freshness (reject if older than 5 minutes)
  const age = Date.now() - parseInt(timestamp);
  const isFresh = age < 5 * 60 * 1000;
  
  return isValid && isFresh;
}
```

Secret is the platform `webhookSecret` (trim before use; used exactly as submitted).

## Keeping up with Slant's API

Slant publishes no changelog, RSS feed or API version header, and `info.version` stayed `2.0.0` when the order statuses changed without notice on 26 Oct 2026 (researched 28 Oct 2026). The nearest things are the blog's service-updates category at slant3d.com/blog, the public `/health/status` and the docs site's status page built on it (`/health`), and the docs' **Technical Support** section, which lists support@slant3d.com and dev4@slant3d.com (docs bundle, 29 Oct 2026). So Studio keeps its own record:

- `Sources/SlantStudio/Resources/slant-openapi-upstream.json` is a byte-for-byte copy of Slant's live spec as last reviewed (28 Oct 2026, sha256 `5ecf678f…`, `ETag: W/"1e457-1a17a0c7070"`, `Last-Modified: Mon, 26 Oct 2026 21:09:58 GMT`; Slant answers `If-None-Match` / `If-Modified-Since` with 304). It is bundled with `openapi.json`. Never hand-edit it.
- `openapi.json` is that spec plus Studio's patches. Every patch carries `x-slant-studio-source: docs` or `live` on the changed operation, parameter, property or schema (or an ancestor), except text appended to Slant's own non-empty `description`; a description Slant doesn't have is a patch and carries a tag. Put the tag on the nearest node that holds the fact, so a live fact never sits under a `docs` tag, and never directly inside a name map (`paths`, `properties`, `schemas`, `responses` and the like), where it would read as one of the map's names. Keep Studio's own behaviour out of Slant's text: it belongs in this file. Edit it only with a Python round trip that leaves an untouched file byte-identical: `json.dumps(obj, indent=2, ensure_ascii=False) + '\n'`. Tests check that both files load, that `openapi.json` keeps every operation in the snapshot, that no source tag sits at the root or directly inside a name map (`OpenAPISnapshotTests`), and that the script's key lists match `SlantAPIChanges.swift` and its `--self-test` passes (`SlantAPIScriptParityTests`).
- `python3 -I scripts/check-slant-api.py` (standard library only, no key) fetches the live spec (https only, no redirects, ≤ 2 MB, 30 s timeout), prints its ETag and Last-Modified, and compares it with the snapshot as parsed JSON: operations added or removed, then contract changes (parameters, enums, `required`, types, properties) per operation and per schema, apart from wording-only changes (`description`, `summary`, `title`, `example(s)`, `externalDocs`: the same keys the app ignores). Unordered lists (`required`, `enum`, `tags`, `type` arrays and every list but `servers` and `prefixItems`) are compared as sets, as the app does. The script also reports changes the app's daily check ignores (`x-` extensions, `info` other than `version`, the top-level `tags` list, parameter order) and says so under the contract changes. It then lists any difference between `openapi.json` and the snapshot that isn't tagged. Exit codes: **0** no change, **1** contract change, **3** wording only, **2** untagged patches (reported only when Slant's side is unchanged), **4** couldn't check (network failure, redirect, too large, not JSON, bad arguments). `--update-snapshot` writes the live bytes over the snapshot after printing the diff (and still exits 1 or 3); `--offline PATH` compares a file instead of fetching; `--self-test` runs built-in fixtures offline and exits 0 or 1. A tag at the root or directly inside a name map, or a tag value other than `docs`/`live`, is itself reported as an untagged patch.
- Run it before every release and whenever Studio's change check reports that Slant's spec changed. On exit 1 or 3, read the diff, run again with `--update-snapshot`, then bring `openapi.json`, Studio and this file into line until the script exits 0: the untagged-patch list then shows where `openapi.json` still differs from Slant. A removed enum value is exactly how the order statuses changed.

## Shopify (optional, seller's own store)

Not a Slant API: Studio talks to the seller's store directly (`ShopifyClient.swift`, `ShopifyImport.swift`, `ShopifyTracking.swift`, `ShopifyOrderMatching.swift`). Requests go only to `https://<handle>.myshopify.com`; custom domains are refused, input is normalised to `handle.myshopify.com` (bare handle, `handle.myshopify.com` or `admin.shopify.com/store/handle`), and redirects are refused.

- **Auth:** a Dev Dashboard app's client ID and secret, exchanged with `POST https://<shop>/admin/oauth/access_token` (form body `grant_type=client_credentials&client_id=…&client_secret=…`); the token is kept in memory only, for `expires_in` (86,400 s if absent, clamped to 60 s–48 h, renewed 60 s early; a read that gets a 401 fetches a new token once, and a mutation renews a token with under 5 minutes left). Or a legacy `shpat_` Admin API token from a custom app made in the store admin, sent as `X-Shopify-Access-Token`. Credentials are in the Keychain (service `SlantStudio`, account `shopify-credentials`, this device only); the shop address is in preferences (`shopifyShopDomain`). Scopes: `read_orders` (or `write_orders`) to import; `write_merchant_managed_fulfillment_orders` (or the assigned/third-party fulfilment-order write scopes) to send tracking, read from the token reply's `scope` or `currentAppInstallation.accessScopes`.
- **Endpoint:** Admin GraphQL `POST https://<shop>/admin/api/2026-10/graphql.json`. Operations by name: queries `StudioShop` (Test Connection: shop name, `myshopifyDomain`, `plan { publicDisplayName partnerDevelopment }`, scopes), `StudioScopes`, `StudioImportOrders`, `StudioFindOrder`, `StudioFulfilmentCheck`; mutation `StudioSendTracking` (`fulfillmentCreate`). 30 s request timeout, replies capped at 4 MB, ephemeral session. Any top-level GraphQL error fails the request.
- **Throttling:** Studio tracks `extensions.cost.throttleStatus` and waits before a request when the bucket is short. HTTP 429 or the `THROTTLED` code is throttled (`Retry-After` honoured, capped at 30 s); reads are retried at most 3 times, each wait ≤ 30 s. Mutations are sent once and never retried (`fulfillmentCreate` has no idempotency key).
- **Fetch from Shopify** (Import Orders): `StudioImportOrders` with `query: "financial_status:paid fulfillment_status:unfulfilled status:open created_at:>=<60 days ago, UTC>"`, oldest first, 8 orders per page (estimated cost 620), at most 250 orders and 30 line items each (an order with more is left out, to import from CSV). Any early stop fails the whole fetch rather than showing a partial list. Read: order `name` (the `sourceOrderId`, such as `#1001`), email, cancellation and statuses, the shipping address (no phone), line items (`id`, `name`, `sku`, `currentQuantity`, visible `customAttributes` as personalisation) and `shopMoney` sale amounts. The result goes into the unchanged import sheet; nothing is sent to Slant until the seller confirms.
- **Draft metadata:** `sourceShop` (fetched orders) and `sourceItems`, compact JSON such as `[{"lineItem":"123","quantity":2}]` with each entry keyed by the line item's numeric ID, else its SKU (never its name, which can carry a buyer's text); written only when every included item has one, with at most 60 entries and 1,000 characters (read back up to 2,000).
- **Send Tracking to Shopify…:** for imported Shopify orders with Slant tracking (≤ 50). A read-only check first (`StudioFindOrder` by exact `name`, then `StudioFulfilmentCheck`: cancellation, existing fulfilments and tracking numbers, one fulfilment order with `CREATE_FULFILLMENT` and ≤ 30 lines). A draft whose `sourceShop` is another store is refused without contacting Shopify; one without `sourceShop` (a CSV import) must match the order's shipping name and postcode and is never ticked automatically. Only the units recorded in `sourceItems` are allocated; too few unfulfilled units blocks the order. Each send re-runs the check, then `fulfillmentCreate` with exactly those fulfilment-order line items, `trackingInfo` (number(s) and company) and `notifyCustomer` (off by default), one order at a time, 0.5 s apart. The first unknown outcome (408/409, 3xx, 5xx, transport error, unreadable reply, cancelled in flight) stops the run; 3 refusals in a row also stop it.
- **Unverified:** live query costs (Studio uses its own estimates), the status code Shopify uses for throttling in practice (429 and `THROTTLED` are both handled), whether scope approval and protected customer data access need extra review for a Dev Dashboard app, how Basic/Starter plans withhold customer names and addresses from custom apps (Studio warns when the plan name contains "basic" or "starter" and treats "not approved to access" errors as withheld data), and whether Slant keeps a 1,000-character `sourceItems` string intact (Slant documents no metadata value length).

- **Balance:** `GET /openapi/v1/balance` → `balance` (Save & Test and Check Balance).
- **Errors:** 402 = not enough credits or the Free plan (which has no API access); 429 = rate or concurrency limit, with `Retry-After` on the rate limit. Running tasks' `Retry-After` is used as the poll interval (2–30 s). Generated files stay on `assets.meshy.ai` for 3 days.
- **Unverified:** whether Convert accepts a repair task's ID; the STL's units and up axis (Studio always rescales to the typed size and offers As Made / Turned Upright); how many triangles an unremeshed model has (a download over 128 MB, about 2.68M STL triangles, is a final stop); the multi-image read shape; the API's test key.

### Tripo3D

`TripoClient.swift`. Tripo's v3 API on one of two regional sites with separate keys: `https://openapi.tripo3d.ai/v3` (international) or `https://openapi.tripo3d.com/v3` (China mainland). Header `Authorization: Bearer <key>`; replies are `{"code": 0, "data": {…}}`, and any other code is an error.

- **Upload:** `POST /v3/files`, multipart with the single field `file` (JPEG or PNG, ≤ 20 MB) → `data.file_token`. Free; any failure counts as not sent.
- **Generation:** `POST /v3/generation/image-to-model` with `input` (the file token), `model: "v3.1-20260211"` (pinned), `texture: false`, `pbr: false` and `face_limit` (clamped to 500–1,500,000, or 2,000,000 with detailed geometry; 500,000 for a display piece and 100,000 for a functional part, simplified on the Mac) → `data.task_id`. GLB only; 20 credits. Higher detail adds `geometry_quality: "detailed"` (+20 credits).
- **Multiview** (two to four photos): every photo is uploaded first, then one `POST /v3/generation/multiview-to-model` with the same options and `inputs`, an array of one-key objects `{"front"|"left"|"back"|"right": <file_token>}` (front required; left and right are the object's own sides, a convention taken from third-party docs). An upload failure means nothing was created. 20 credits, as for one photo.
- **Tasks:** `GET /v3/tasks/{id}` (`status` queued, running, success, failed, banned, expired, cancelled; `progress`; `output.model_url`).
- **Convert:** `POST /v3/models/convert` with `input` (the generation task) and `format: "STL"` (or `"3MF"`), 5 credits; no `face_limit` is sent, so every face is kept. The client adds `pivot_to_center_bottom: true` only when asked for the origin at the bottom, which makes it a 10-credit conversion; Generate a Replica never asks (Studio places the model itself), so a replica costs about 25 credits.
- **Balance:** `GET /v3/account/balance` → `data.balance`, `data.frozen`.
- **Errors:** Tripo's `code` is read only on a 2xx or a 4xx other than 408/409; otherwise the HTTP status decides, so an unclear create stays unknown. HTTP 429, code 1007 (rate) or 2000 (concurrency, with `Retry-After`) is rate-limited; 2010 is not enough credits; 1000/1001 are treated as a bad key; a readable 2xx refusal is a refusal.
- **Conversion links:** an `output` link is kept only if it passes the download checks; an STL/3MF extension is preferred, but a link with any other or no extension is accepted and its content decides (ZIP → 3MF, glTF refused, else parsed as STL).
- **Unverified:** the download host; whether `model_url` links expire after about 5 minutes; whether a `face_limit` of 500,000 is honoured; what "left" means to Tripo; a plain file token as a multiview value; the link format.

### Polling and unknown outcomes

`ImageTo3D.swift`. Status reads every 4 s, up to 10 minutes per stage; transient failures (transport, 408, 5xx, unreadable reply) back off as start × 2^n, capped at 60 s, and 5 in a row stop the run. A 429 waits for `Retry-After` (seconds or HTTP date, capped at 120 s; 16 s without one) and doesn't count as a failure. The API session never follows redirects (a 3xx is unknown) and caps JSON replies at 2 MB. A create whose outcome is unknown (408, 409, 3xx, 5xx, transport error, unreadable or oversized reply, cancelled in flight) is recorded in `ImageTo3DConnection.unconfirmedRequests` (memory only, ≤ 10 with an overflow flag, kept through key and service changes until quit); any other 4xx (including 402 and 429) means not sent. A stop after a task exists keeps a resume point (task and conversion IDs), so **Keep Waiting** polls or downloads the same task without a new create.

### Downloads

Generated models are downloaded (`imageTo3DDownloadURLProblem`) only over https, from a named host that isn't `localhost`, `*.local` or `*.localhost` or an IP literal (checked by name; DNS isn't resolved), with no user, password or fragment. Size ≤ 128 MB, checked against `Content-Length` and while reading; empty bodies refused; 15-minute timeout; 403/404 reported as expired. The download session is ephemeral, sends no `Authorization` header or cookies, and checks every redirect against the same rules. Files land in a `SlantStudio-Generated3D-<UUID>` temporary folder that is removed after processing.
